# 수입 날짜 수정 권한 오류와 실패 대기 건

## 배포 수정

기존 내역 화면에서 입금 처리된 수입의 실제 날짜를 바꾸면 이전 저장 경로가 revision을 유지해 Firestore 규칙에 거부됐다. 금액과 날짜를 동시에 수정하면 금액 연산 후 별도 일반 쓰기로 날짜를 저장해 같은 문제가 생겼다.

`17b26e0a384e4585ea526f0399a52c231bc5c72c`는 보호 필드 변경을 revision 검사 작업으로 묶는다. 연결된 회차와 거래의 금액 수정은 한 작업으로 처리하며 실제 거래일을 바꿔도 예정 회차/예산 주기를 바꾸지 않는다. 연결된 회차를 찾지 못한 금액 변경은 중단한다. UI는 수정 오류를 폼에 표시한다. 규칙 파일과 Android 네이티브는 변경하지 않았다. 단위 테스트 703개와 규칙 테스트 33개를 통과했다.

## 다음 단계: 이전 버전의 실패 대기 건 복구

이전 앱이 날짜를 바꾼 로컬 기록과 실패한 일반 쓰기를 이미 보관했다면, 새 저장 경로만 배포해도 기존 대기 요청은 자동으로 새 형식이 되지 않는다. 따라서 permission-denied가 발생한 수입 일반 쓰기에 한해 복구 경로를 추가했다.

복구는 Firestore 트랜잭션에서 현재 서버 기록을 다시 읽고, 수정 번호·금액·분류·연결 거래·메모 등 날짜 이외의 값이 동일할 때만 실제 날짜와 발생 시각을 변경한다. 수정 번호는 정확히 1 증가한다. 회차와 금액은 변경하지 않는다. 당시 폼이 추가한 빈 태그/기본 결제방식/null 필드는 의미가 같은 값으로 비교한다. 영수증·음성 데이터, 잘못된 날짜, revision이 없는 기록, 지출 기록에는 적용하지 않는다.

작업 ID는 대기 건 ID에서 결정해 응답 유실 후 재시도도 중복 적용하지 않는다. 성공 후 해당 대기 건을 제거하고 로컬 수정 번호를 최신 값으로 맞춘다. 네트워크 요청 중 사용자가 추가로 수정한 캐시는 덮어쓰지 않는다.

다른 기기에서 이미 수정했거나 날짜 외 변경이 있으면 자동 병합하지 않는다. 시도한 변경 내용을 충돌 확인 목록에 보존하고 서버의 최신 값을 캐시에 반영하며, 다음 대기 쓰기는 계속 처리한다. 네트워크 오류는 원래 대기 상태로 유지한다. 거래 삭제·규칙 완화·운영 데이터 마이그레이션은 없다.

후속 수정 테스트는 날짜 재시도, 서버 변경 거부, 금액/메모 변경 거부, 멱등성, 잘못된 날짜, 로컬 동시 편집 보존, 충돌 시 시도한 값 보존, 후속 쓰기 진행, 오프라인 대기 유지를 검증한다. 실제 운영 금융 데이터에 복구 작업을 실행하지 않았다. 운영 적용 여부는 이 후속 변경을 포함한 커밋의 별도 배포 상태로 구분한다.

검증: 후속 수정을 포함해 타입 검사, 전체 단위 테스트 718개, ESLint 오류 0개, 웹·서버 빌드를 통과했다. 운영 확인은 배포한 커밋과 `/api/live-update` 버전을 대조한다.
