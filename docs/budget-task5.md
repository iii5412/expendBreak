# Task 5: 분석, 데이터 관리, 배포 패키징

## 화면과 집계

실제 계정은 기존 PIN·세션 확인을 거친 `/?view=budget`, 로컬 체험은 `budget-app.html?mode=local`이다. 기본 `/` 진입 화면은 유지한다. 설치된 앱에서는 관리·설정 상단의 ‘새 예산 화면 열기’로 진입하고 새 화면의 관리에서 기존 화면으로 돌아올 수 있다.

분석 탭은 Recharts로 수입/지출 막대, 지출 구성 도넛, 일별 누적 변동지출과 전체 주기 한도 선, 카테고리별 금액 예산/횟수 쿠폰 사용률을 보여 준다. 색 외에도 항목명·원/회/%·실선/점선과 숫자 목록으로 구분한다. 지정된 회계 주기를 따르고 오늘까지 확정된 거래만 집계한다. 이체와 카드 대금 결제는 어댑터에서 제외한다. 고정비는 총지출/도넛에 포함하되 변동지출 선과 금액/쿠폰 사용률에는 포함하지 않는다. 일회성 변동지출은 실제 지출에 포함한다. 미래 누적값은 0원으로 오해하지 않도록 비워 둔다.

관리 → 예산과 쿠폰 기준 → 카테고리별 변동지출 한도에서 개별 금액 한도를 정한다. 0원은 별도 한도 없음이며 임의의 예산을 배정하지 않는다. 새 `categoryAmountLimits`는 기존 예산·프로필 쓰기에 선택 필드로 저장한다. 삭제된 옛 `categoryLimits`를 재사용하지 않으며 전체 변동지출 한도를 자동 변경하지 않는다.

## 전체 CSV

관리 → 내보내기와 초기화 → 전체 거래 CSV 내보내기. 실제 계정에서는 저장 대기를 먼저 동기화하고 Firestore 서버의 전체 거래/카테고리를 읽는다. 최근 90일 캐시나 브라우저 저장 용량에 의존하지 않으며, 오프라인일 때 일부 기록만 내보내지 않고 실패를 알린다. 실서버 전체 기록 읽기는 로컬 자격 증명이 없어 대체 데이터로 검증했다.

UTF-8 BOM, CRLF, CSV 따옴표 이스케이프, 스프레드시트 수식 실행 방지를 적용한다. 이체·결제 등 원장 행도 내보내며 거래 역할/ID/예산 주기/지출 성격을 별도 열로 구분한다. CSV는 거래 목록이고 전체 앱을 복구하는 백업 파일은 아니다. 로컬 체험 CSV는 체험 데이터만 담는다. Chrome 다운로드를 확인했으며 APK의 파일 저장 동작은 실기기 확인이 남아 있다.

## 사용자 요청에 의한 가계부 초기화

관리에서 삭제 범위를 펼치고 ‘삭제 전 확인’ 후 `내 가계부 초기화`를 정확히 입력해야 최종 삭제 버튼이 활성화된다. 기능 구현 과정에서 실제 삭제는 실행하지 않았다.

기존 `resetAllData`는 영수증 Storage 삭제, 계정 데이터 삭제, 로컬 정리/재초기화 순서를 따른다. 저장 대기가 동기화되지 않으면 시작하지 않고 계정 전환도 확인한다. Firestore의 금액 변경 이력은 클라이언트에서 삭제 금지이므로 기존 브라우저 배치 삭제를 `/api/account/reset-data`로 교체했다. 이 경로는 서명된 계정 세션과 정확한 확인 문구를 요구한다. 대상 UID/경로를 요청에서 받지 않고 세션 UID 아래 허용된 가계부 컬렉션만 400건씩 삭제한다. 월급 준비금·결제 묶음·계좌 통합 기록·금액 변경 이력도 포함한다. 실패하면 성공으로 표시하지 않고 재시도할 수 있다. 부분 삭제가 일어날 수 있으므로 미완료 메시지를 확인해야 한다.

로그인 계정/PIN, 세션 관련 메타데이터, 기존 이관 완료 표시, 일일 AI 사용량은 유지한다. 이관 표시를 지우면 옛 데이터가 재유입될 수 있고 AI 사용량 삭제는 호출 한도를 우회할 수 있다. 따라서 UI 이름도 ‘계정 가계부 데이터 초기화’이며 계정 탈퇴나 로그인 자격 삭제를 뜻하지 않는다. Firestore/Storage 규칙을 완화하지 않았다.

## PWA와 Cloud Run

기존 `manifest.webmanifest`와 모바일 메타 태그를 유지하며 개인·가족 가계부 설명과 새 예산 화면 바로가기를 추가했다. 기존 설치 주소 `/`는 유지한다. 운영 Express는 `PORT` 우선, 미지정 시 8080, `0.0.0.0`에서 API와 `dist`를 제공한다. 개발 기본 포트 3000은 유지한다.

Dockerfile은 production 의존성 설치 단계와 비루트 런타임 단계로 분리했다. 기존 GitHub workflow가 같은 커밋에서 웹/서버/Android 화면 묶음을 빌드하고 그 결과만 이미지에 넣는 방식을 유지한다. 소스 빌드를 Docker 안에서 다시 수행해 검증된 Android 묶음과 버전이 달라지지 않도록 했다. `.dockerignore` 허용 목록으로 환경 파일·키·로컬 내보내기 파일을 제외한다. 생성된 `build/`, `live-update/`는 ESLint 대상에서 제외한다. Docker CLI는 있으나 Docker Desktop Linux 엔진이 꺼져 있어 컨테이너 이미지 빌드/기동은 검증하지 못했다.

## Checkpoint 3: 기존 자동 배포 사용

현재 저장소는 이미 GitHub CI → Cloud Run `service` (`asia-east1`) 자동 배포가 구성되어 있다. 처음 프로젝트를 만드는 일반 안내 대신 [배포 운영 절차](DEPLOY-RUNBOOK.md)를 따른다. AI Studio Sync/Deploy 버튼으로 운영을 덮어쓰거나 서울 리전에 새 서비스를 만들지 않는다.

1. 로컬 검토 후 이 변경을 main에 push하는 승인을 별도로 받는다. 이번 작업에서는 커밋/push/배포를 하지 않았다.
2. 승인 후 기존 workflow가 CI, 웹/서버/Android 묶음 빌드, 트래픽 없는 후보 배포를 수행한다. 후보의 `/api/live-update`, `/`, `/api/auth/status` 검증을 통과하면 트래픽을 전환한다.
3. 기존 배포 주소에 `/?view=budget`으로 접속해 PIN 로그인 후 분석/CSV를 확인한다. Gemini 키는 서버 Cloud Run 환경변수에서만 관리하며 실제 AI 호출은 별도 확인한다. Vite 설정은 빌드 시 적용되므로 런타임 환경변수만 추가해서 바뀌지 않는다.
4. Android Chrome에서 기존 HTTPS 주소 → 메뉴 → 앱 설치/홈 화면에 추가. 기존 APK는 새 화면 묶음을 다운로드한 뒤 다시 시작하면 적용된다. 네이티브 변경이 없어 새 APK나 versionCode 증가는 필요 없다. 자동 배포가 기본 진입 화면을 새 예산 화면으로 강제 전환하지는 않는다.

## 검증

최종 검증: `npm run lint` 통과, `npm test` 88개 파일·698개 테스트 통과, `npm run lint:eslint` 오류 0개(기존 경고 236개), `npm run build` 통과. 타입 검사와 빌드를 동시에 실행하면 생성 파일 교체와 충돌할 수 있어 최종 타입 검사는 빌드 후 단독 실행했다. 신규 테스트는 집계/설정 보존, CSV BOM·이스케이프·수식 방지, 서버 전체 기록 읽기 실패, 초기화 인증·확인 문구·다른 계정 격리·배치 처리·재시도, Cloud Run 포트를 다룬다. 로컬 체험 브라우저에서 360px 레이아웃, 금액 한도 저장/사용률 반영, CSV 실제 다운로드와 BOM, 초기화 확인/취소를 확인했다. 실금융 데이터 삭제·운영 배포·실제 Gemini 호출은 하지 않았다.
