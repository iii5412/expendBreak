# 지출브레이크 8·9월 진단 점검 보고서

작성일: 2026-09-07 · 점검 코드: `caf21ea` · 기준 시각: 2026-09-07 14:13 KST

## 판정

**월별 계산을 재실행했을 때 내보낸 값과는 모두 일치하지만, 계산 기준과 화면 표시에서 수정할 문제 5개를 확인했다.** 가장 먼저 고칠 것은 선택 월에 따라 동일한 미래 월의 카드 예상액이 달라지는 문제다. 거래 연결이 끊어지거나 수입·지출 카테고리가 뒤바뀐 사례는 이번 데이터에서 발견하지 못했다.

앱 소스나 운영 데이터는 수정하지 않았다. 이 보고서와 로컬 분석 스크립트만 작성했다. 아래 금액은 앱 기록에 대한 검증 결과이며 실제 은행 잔액·카드 청구서와 대조한 결과는 아니다.

회계 기간과 소비 기간을 다르게 쓰는 것은 현재 코드가 의도한 설계다. 9월의 `confirmedExpenses=0`과 `confirmedVariableExpenses=447660`이 함께 존재하는 것만으로 거래 유실이라고 판단할 수 없다. 9/7에는 9월 회계 기간이 아직 시작되지 않았지만 9월 소비는 이미 발생했다.

## 3. 확인된 계산·표시 문제

### B1 · P1 — 선택 월만 바꿔도 같은 11월 카드 예상액이 7,890원 달라짐

**근거:** `calculations.futureCommitments.months`의 2026-11 항목.

| 11월 예측 | 8월 선택 시 | 9월 선택 시 | 차이 |
|---|---:|---:|---:|
| 카드대금 | 896,910원 | 904,800원 | 7,890원 |
| 전체 지출 | 5,162,946원 | 5,170,836원 | 7,890원 |

원인은 삭제 처리된 ‘쿠팡’ 정기 원본(`tmpl_1786339893708_3slcy`)과 10/12 확인 대기 일정이다. 8월 선택에서는 원본이 계산 입력에 남아 `archivedAt`을 확인할 수 있으므로 카드 계산에서 제외된다. 9월 선택에서는 원본만 입력에서 빠지고 전체 일정은 남는다. 카드 계산은 원본이 없으면 일정의 결제 방식·카드 snapshot을 사용하므로 7,890원을 다시 포함한다.

전체 원본의 삭제 상태를 함께 전달하거나, 삭제된 원본의 미래 일정을 일관되게 제외한 실험에서는 양쪽 모두 896,910원이 나왔다. 이것은 기존 코드의 ‘삭제된 카드 원본은 예측에서 제외’ 정책을 적용한 결과이며 실제 카드 청구액을 확정한 것은 아니다.

**개선:** 미래 예측에는 현재 선택 월에 종속되지 않는 원본 참조 집합을 사용한다. 원본 누락과 삭제 상태를 구분하고, 이미 불러온 월별 계획의 유지 정책을 계좌·카드에 일관되게 적용한다. 월 전환 전후 동일 대상 월의 금액이 같다는 회귀 검증을 추가한다.

코드: [선택 월에 따른 원본 필터](../src/App.tsx), [전체 일정 필터](../src/App.tsx), [카드 일정의 삭제 확인](../src/utils/cardPayments.ts).

### B2 · P2 — 6주기 예측이 월별 계획 금액을 무시함

**근거:** 9월 요약의 계좌 고정 지출은 4,267,996원인데, 같은 9월의 6주기 예측은 4,266,036원이다. 차이 1,960원은 ‘가스비’ 원본 기본금액 10,040원과 9/10 일정 금액 12,000원의 차이와 일치한다. 8월도 요약 4,321,116원과 예측 4,266,036원이 55,080원 다르다.

현재 미래 예측은 계좌 고정 지출을 원본 `defaultAmount × 예정 횟수`로만 합산한다. 해당 월에 이미 기록된 실제 거래·월별 일정 금액·건너뜀 상태를 반영하지 않는다. 카드 예측은 일정과 거래를 사용하므로 한 차트 안에서도 기준이 다르다.

**영향:** 사용자가 월별 금액을 수정해도 ‘앞으로 6주기에 이미 정해진 지출’에는 반영되지 않는다. 현재 파일의 9월 차이는 1,960원이지만 큰 항목의 변경이나 건너뜀에서도 같은 구조가 작동한다.

**개선:** 이미 생성된 월은 완료 거래와 유효한 월별 일정부터 계산하고, 아직 생성하지 않은 일정에만 원본 기본금액을 적용한다. 원본 기준 시나리오를 유지한다면 월별 계획 기준과 명확히 분리해 표시한다.

코드: [원본 금액만 사용하는 합산](../src/utils/futureCommitments.ts), [‘이미 정해진 지출’ 표시](../src/components/FutureCommitmentsCard.tsx).

### B3 · P2 — 종료된 소비 월에 남은 날짜·미래 소진 안내가 표시됨

**근거:** 9/7에 내보낸 8월 생활비 기간은 8/31에 끝났지만 `spendDaysRemaining=1`, `projectedDepletionDate=2026-09-07`이다. 화면 코드 그대로라면 ‘8/1–8/31 · 남은 1일’과 ‘지금 속도면 2026-09-07에 생활비가 끝납니다’가 함께 표시된다.

남은 일수를 항상 최소 1로 제한하고, 잔여 한도가 음수이면 기간 종료 여부와 무관하게 조회 당일을 소진 예정일로 지정한다. 또한 아직 시작되지 않은 9/10–10/9 기간은 총 30일인데 `daysRemaining=31`로 계산된다.

**개선:** 기간 상태를 시작 전·진행 중·종료로 구분한다. 종료된 소비 월은 ‘마감’과 실제 사용액·초과액을 표시하고, 남은 날짜는 0으로 한다. 0 나눗셈 방지는 계산 내부에서만 처리한다. 과거 월에는 미래 예측 문구를 표시하지 않는다. 실제 한도 초과일을 보여주려면 현재 한도와 당시 한도가 같았는지까지 구분한다.

코드: [남은 일수·소진일 계산](../src/utils/calculations.ts), [남은 날짜·소진 안내](../src/components/DashboardView.tsx).

### B4 · P2 — 가용 재원 0원을 ‘999% 사용’으로 표시함

**근거:** 9월 `spendableLimit=0`, `confirmedVariableExpenses=447660`, `budgetUsagePercent=999`.

999는 0으로 나누는 상황을 피하기 위한 임의의 대체 숫자다. 실제 비율이 아닌데 대시보드와 분석 화면에 그대로 퍼센트로 출력된다. 사용자 설정 한도 1,800,000원에 대한 사용률은 약 24.9%이지만, 앱은 고정 지출을 뺀 가용 재원이 0원이라는 이유로 999%를 표시한다. 24.9%만으로 경고를 대체해도 재원 부족이 숨겨지므로 두 상태를 구분해야 한다.

**개선:** ‘설정 한도 사용률 24.9%’와 ‘고정 지출 반영 후 가용 재원 없음’을 별도 표시한다. 가용 재원 기준 비율은 계산 불가 상태로 모델링하고, 숫자 999를 사용자에게 노출하지 않는다. 재원 부족 684,736원과 이미 사용한 생활비 447,660원도 구분해 설명한다.

코드: [비율 계산](../src/utils/calculations.ts), [대시보드 표시](../src/components/DashboardView.tsx), [분석 화면 표시](../src/components/AnalyticsView.tsx).

### B5 · P2 — 거래내역 ‘지출’ 합계에 카드 정산과 대체된 과거 기록이 함께 포함됨

**재현:** 8월 선택 → 거래내역 → 이번 주기 → 전체. 첨부 거래와 화면의 필터·합산 로직으로 재계산하면 지출이 **15,156,664원**이다. 같은 회계 기간에 대한 요약 `confirmedExpenses`는 **7,602,646원**이다.

차이 7,554,018원의 구성은 다음과 같다.

| 내역 | 합계 |
|---|---:|
| 별도의 카드 납부 완료 거래 3건 | 3,720,000원 |
| 자동 카드대금으로 대체되어 계획에서 제외된 기존 정기 거래 3건 | 3,834,018원 |
| 합계 차이 | 7,554,018원 |

계획 요약은 대체된 기존 카드대금 거래를 제외하고 카드 정산도 소비에서 제외하지만, 거래내역은 원본 전체를 받아 선택된 거래의 `type`만으로 합산한다. 그 결과 소비·정산·대체 기록이 모두 ‘지출’과 ‘순액’에 들어간다. 원본 기록을 보존하는 것 자체는 문제가 아니며, 이 차이를 실제 추가 소비라고 해석하면 안 된다.

**개선:** 거래내역에서 소비 지출, 카드 납부, 이체, 대체된 기록을 구분한다. 대체된 거래는 설명 배지와 근거 연결을 남기고 소비 합계에서는 제외한다. 선택 행의 원시 합계를 유지한다면 명칭을 ‘선택 기록 금액 합계’로 바꾸고 소비 지출 합계를 따로 제공한다. 거래를 자동 삭제하는 방식은 권하지 않는다.

코드: [거래 필터·합계](../src/components/HistoryView.tsx), [원본 거래 전달](../src/App.tsx).

| 삭제 원본의 미래 일정 | 삭제된 원본 4개의 확인 대기 일정 5개가 10·11월에 남아 있다. 합계 372,890원. | 현재 설계는 원본을 삭제해도 이미 불러온 월별 계획을 유지한다. 이 자체를 삭제 실패로 단정하지 않는다. 삭제 시 어느 월의 일정이 남는지 안내하고 유지·제외 정책을 명시해야 한다. B1은 그 유지 상태를 계산기가 일관되게 해석하지 못하는 별도 문제다. |
| 잔액 기록 | 계좌 16개 모두 0원. 8개는 기준일 없음, 8개는 8/11 기준이다. | 실제 0원인지 미입력 기본값인지 구분할 수 없다. 잔액 기반 예측은 실잔액 검증 근거로 사용할 수 없다. |

원본이 없는 일정 14개도 발견했지만 전부 `skipped`이고, 이번 재현에서는 지출 합산에 포함되지 않았다. 이를 활성 지출 중복으로 보고하지 않는다.

## 5. 기존 기능 개선 제안

1. **기간 연결을 명확히 한다.** 현재 9월 홈에는 생활비 447,660원이 표시되지만 거래내역 기본 ‘이번 주기’에는 9/10 이후 거래만 표시되어 0건이다. 생활비 숫자를 누르면 9/1–9/30의 같은 소비 목록으로 이동하도록 한다. 소비 월·급여 회계 기간 전환과 실제 날짜 범위를 함께 표시한다.
2. **계산 근거를 펼쳐 볼 수 있게 한다.** ‘수입 → 계좌 고정 지출 → 카드대금 → 사용 가능 재원 → 설정 한도 → 생활비 사용’의 각 금액을 해당 항목 목록과 연결한다. 8월 30만 원과 9월 180만 원처럼 월별 한도가 달라졌을 때 적용 한도를 명확히 보여준다.
3. **정기 원본과 월별 계획의 차이를 보여준다.** 원본 수정·삭제 후 영향받는 월, 기존 금액, 변경 금액, 유지되는 일정 수를 표시한다. ‘새로 불러오기’ 전에 완료 거래·월별 수정액·건너뜀을 어떻게 처리할지 미리 확인할 수 있게 한다.
4. **카드 추정에 신뢰 상태를 붙인다.** ‘확정 청구액’, ‘기록 기반 추정’, ‘사용 기록 없음’을 구분한다. 미래 차트의 ‘확정 지출’ 표현도 추정액을 포함할 때는 바꾼다. 수동 카드대금을 대체할 때 0원 추정으로 조용히 바뀌지 않도록 차이를 안내한다.
5. **잔액 0원과 미입력을 구분한다.** 별도 입력 완료 상태·기준일을 저장하고 오래된 잔액을 표시한다. 현재 잔액 타임라인은 0원이 아닌 잔액이 하나도 없으면 시작 잔액이 없다고 처리하므로, 사용자가 확인한 0원도 미입력과 구분되지 않는다.
6. **진단 내보내기를 강화한다.** 앱 버전·플랫폼·계산 기준 시각·실제 회계/소비 기간·동기화 미반영 건수·계산 입력 선택 사유를 추가한다. Android 저장은 스트림 종료 후 성공을 확정하고 저장 크기/JSON 유효성을 확인한다. 앞서 전달된 0바이트 파일은 생성·전달 중 어느 단계의 문제였는지 확정하지 못했다. 이번 두 파일은 정상이다.
7. **사용자에게 보이는 기준을 검증하는 테스트를 추가한다.** 월 전환 후 같은 미래 월 금액 유지, 월별 수정/건너뜀 반영, 종료 월 안내, 0원 재원 비율, 홈에서 거래내역으로 이동 시 합계 일치를 우선한다. 기존 테스트 통과만으로 이 교차 화면 문제는 발견되지 않았다.

## 6. 검증 결과와 한계

- JSON 파싱과 선언된 주요 건수를 확인했다. 두 스냅샷의 공통 원본 레코드가 동일함을 비교했다.
- 두 월의 요약, 카드 정산 요약, 6주기 예측을 원본 입력·분류 ID·내보낸 시각으로 다시 실행하여 전체 객체가 일치함을 검증했다.
- 처리 완료 일정 33개의 연결 거래, 정기 원본 ID, 발생 키, 금액, 수입/지출 유형이 일치했다. 정기 거래에서 연결 일정을 찾지 못한 사례도 없었다.
- 거래·정기 원본의 카테고리 유형 불일치, 거래의 계좌·카드·정기 원본 참조 누락, 일정 발생 키 중복은 발견하지 못했다.
- 기존 자동 테스트 **36개 파일, 271개 테스트 통과**. TypeScript 검사 `tsc --noEmit` 통과.
- 실제 Android 화면 조작·은행 청구서 대조·서버 로그·Firestore 동기화 이력·음성/영수증 원본·SMS 수신 경로는 이 진단 파일만으로 검증하지 못했다. 거래에 구조화된 할부 계획은 0건이므로 실제 할부 데이터에 대한 검증 결과로 확대할 수 없다.
- 화면 문제는 실제 화면 캡처가 아니라, 첨부 데이터에 현재 컴포넌트의 필터·계산·문구를 적용해 확인했다. 진단 파일에 앱 버전이 없어 설치 APK와 현재 소스의 완전한 동일성은 확인할 수 없지만, 내보낸 계산 결과는 현재 코드로 모두 재현된다.

재현 파일: [계산 재현 스크립트](../scripts/audit-diagnostics-replay.ts), [데이터 점검 스크립트](../scripts/audit-diagnostics.mjs). 재현 결과 JSON은 로컬 `artifacts` 폴더에 생성된다.

권장 처리 순서는 **B1 예측 일관성 → B2 월별 계획 반영 → B3·B4 날짜/상태 표시 → B5 합계 구분 → 데이터 중복 후보 확인과 사용성 개선**이다.
