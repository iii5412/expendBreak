# ExpendBreak 급여일 현금흐름 모델 PRD

작성일: 2026-08-12
대상 버전: 현재 `main` (cf2ccf1) 기준
선행 문서: `PRD-usability-improvements.md`, `PRD-life-ledger-expansion.md`, `IMPLEMENTATION-STATUS.md`

## 1. 배경

`PRD-usability-improvements.md` P1-2로 급여일 기준 회계 주기(`monthStartDay`)가 도입됐고, 이후 카드 정산·할부 예측·카드대금 자동 생성이 순차적으로 붙었다. 기간 개념 자체는 사용자 패턴과 맞춰졌다.

그러나 그 위에 올라간 **금액 계산 모델은 여전히 달력 월 가계부의 것**이다. 그 결과 화면이 내놓는 숫자가 사용자의 실제 의사결정("지금 얼마 남았고, 앞으로 얼마씩 써야 하나")과 어긋난다.

### 사용자의 실제 패턴

```
10일 아침   급여 입금
10일 점심   고정지출 이체 (월세·통신비·보험 등) + 카드대금 결제
10일 이후   통장에 남은 돈으로 다음 달 9일까지 생활
```

이 사용자에게 필요한 숫자는 단 하나다. **"10일 점심 이후 통장에 남는 돈"**, 그리고 그것을 남은 날로 나눈 값.

### 현재 앱이 내놓는 숫자

코드 전수 점검과 위 패턴을 재현한 시뮬레이션(급여 300만, 계좌 고정지출 78만, 전월 카드 사용 90만, 이번 주기 카드 사용 30만, 용돈 한도 100만) 결과:

| 항목 | 앱 표시 | 실제 | 차이 |
|---|---|---|---|
| 급여일에 먼저 확보할 고정지출 | 780,000원 | 1,680,000원 | **−900,000원** |
| 저축 예정액 | 1,220,000원 | 320,000원 | **+900,000원** |
| 다음 급여일까지 쓸 현금 | 표시 없음 | 1,320,000원 | — |

차이는 정확히 카드대금 90만원이다. 이 앱은 사용자가 매달 실제로 이체하는 돈의 한 축을 계산에서 통째로 누락하고 있다.

### 근본 원인

앱이 **두 개의 회계 기준을 한 지표 안에 섞어 쓴다.**

| 기준 | 질문 | 현재 구현 |
|---|---|---|
| 발생주의 | "이번 주기에 얼마 썼나" | 카드를 긁은 시점에 지출 계상 (`confirmedVariableExpenses`) |
| 현금주의 | "통장에서 얼마 나가나" | 급여일 이체 + 카드대금 — **구현 안 됨** |

`remainingAllowance` 하나가 두 역할을 겸하려다 어느 쪽으로도 정확하지 않게 됐다. 카드대금은 두 기준의 경계에 걸친 유일한 항목이라 그 틈으로 빠져나갔다.

이 문서는 계산 모델을 두 트랙으로 명시적으로 분리하고, 그 위에 급여일 사용자를 위한 화면과 흐름을 재설계하는 것을 범위로 한다.

## 2. 목표와 비목표

### 목표

- 사용자가 급여일에 **"이번 주기에 쓸 수 있는 돈"** 하나를 확정하고, 그 숫자가 주기 내내 소비 외의 이유로 흔들리지 않게 한다.
- 모든 금액이 **정확히 한 트랙 × 한 주기에** 속하도록 계산 모델을 정의하고, 이를 불변식(invariant)으로 테스트에 고정한다.
- 카드 사용 → 청구 → 결제의 시차를 사용자가 볼 수 있게 하고, 그 시차 때문에 생기는 착시("이번 달 썼는데 왜 다음 달에 또 나가지")를 제거한다.
- 화면마다 다른 "고정지출" 정의를 단일 계산 함수로 통일한다.
- 급여일 아침의 앱 상태를 정상으로 만든다. (현재는 급여 확정 전까지 사용률 999%, 위험 등급)

### 비목표

- 은행/카드사 자동 연동 (수동 입력·확정 전제는 유지)
- 복식부기 도입 (트랙 분리는 개념 수준이며 계정과목을 만들지 않는다)
- 다중 통화·다중 사용자
- 디자인 시스템 전면 리뉴얼 (기존 slate/rose/emerald 팔레트 안에서 위계만 재정의)
- 카테고리 체계·AI 분류 로직 변경

## 3. 현황 진단

코드 전수 점검으로 확인한 지점만 기재한다. 재현 수치는 §1의 시나리오 기준이다.

### 3.1 카드대금이 예산 계산에서 완전히 누락됐다 (회귀)

[App.tsx:243](src/App.tsx:243)의 `duplicateCardSettlementTemplateIds`는 사용자가 수동 등록한 "카드대금" 정기항목을 중복으로 판정해 `planningRecurringTemplates` / `planningRecurringOccurrences` / `planningTransactions`에서 **제외**한다.

이를 대체할 자동 생성 카드대금(`cardSettlementSummary`)은 [App.tsx:319](src/App.tsx:319)에서 별도로 계산되지만, [calculateMonthSummary](src/utils/calculations.ts:194)에는 **전달되지 않는다.** 함수 시그니처에 카드 인자가 아예 없다.

결과적으로 cf2ccf1 이전에는 수동 항목으로나마 고정비에 잡히던 카드대금이, 지금은 어떤 예산 총계에도 들어가지 않는다. `disposableAfterFixed`, `plannedSavings`, `forecastSavings`, `spendableLimit`이 모두 카드대금만큼 낙관적이다.

### 3.2 급여 확정 전 대시보드가 붕괴한다

[calculations.ts:285](src/utils/calculations.ts:285)의 `totalIncome = confirmedIncome`은 미확정 정기 수입을 의도적으로 배제한다. 급여일 아침, 정기 수입 항목을 "거래 확정"하기 전 상태의 실제 출력:

```
오늘 안전 용돈     0원
남은 용돈         -300,000원
용돈 사용률        999%   →  배지: "한도 초과 (100%+)"
저축 예정액       -1,780,000원
```

급여일 기준 앱에서 급여일 아침의 확정 대기 상태는 예외가 아니라 **정상 경로**다. 사용자가 앱을 가장 신뢰해야 할 순간에 화면 전체가 위험 신호를 낸다.

### 3.3 "고정지출"의 정의가 화면마다 다르다

| 화면 | 재현 값 | 계산식 | 위치 |
|---|---|---|---|
| 대시보드 | 780,000 | 정기 지출 전체 (카드 결제분 포함), 카드대금 제외 | [DashboardView.tsx:227](src/components/DashboardView.tsx:227) |
| 정기 관리 | 1,680,000 | 계좌 정기지출 + 카드대금 | [RecurringPaymentView.tsx:180](src/components/RecurringPaymentView.tsx:180) |
| 설정 > 정기 | 1,680,000 | (정기 전체 − 카드 결제 정기) + 카드대금, 별도 식 | [ManagementView.tsx:429](src/components/ManagementView.tsx:429) |

같은 개념이 세 곳에서 독립적으로 계산된다. 값이 우연히 일치하는 경우에도 유지보수 시 갈라진다.

예산 편집 화면의 권장 한도 미리보기([ManagementView.tsx:174](src/components/ManagementView.tsx:174))는 카드대금이 빠진 `summary.disposableAfterFixed`를 쓰므로, 사용자가 감당할 수 없는 용돈 한도를 권장한다.

### 3.4 카드 이용기간 모델이 없다

[cardPayments.ts:218](src/utils/cardPayments.ts:218)의 `calculateMonthlyCardSettlementSummary`는 `_monthStartDay`를 의도적으로 무시하고 달력 월을 쓴다. "이번 달 사용분이 다음 달 결제된다"는 단일 가정이다.

**(a) 결제일이 급여일보다 빠르면 기간 밖으로 나간다.**

| billingDay | 산출 결제일 | 주기(08-10~09-09) 내 |
|---|---|---|
| 5 | 2026-08-05 | **아니오** |
| 14 | 2026-08-14 | 예 |
| 25 | 2026-08-25 | 예 |

`billingDay < monthStartDay`인 카드는 "8월 카드대금"으로 표시되지만 그 주기에 빠져나가지 않는 돈이다.

**(b) 이용기간 마감일 개념이 없어 한 달치가 밀린다.**

실제 카드는 결제일마다 이용기간이 정해져 있다(예: 신한 25일 결제 = 전월 12일 ~ 당월 11일 사용분). 8/5 사용분은 실제로 8/25 결제인데 앱은 9/25로 잡는다. `PaymentCard`에 마감일 필드가 없는 것이 원인이다.

**(c) 같은 화면에 기준이 다른 두 숫자가 나란히 있다.**

대시보드의 "이번 달 카드 사용·예정" 타일은 급여 주기 기준([App.tsx:307](src/App.tsx:307)), 바로 옆 "이번 달 계좌 고정 출금"은 달력 월 기준 정산액이다.

### 3.5 카드 결제 고정지출이 두 주기에 걸쳐 이중 노출된다

카드로 결제되는 통신비 8만원은 다음 두 곳에 동시에 존재한다.

- 8월 `totalExpectedFixedExpenses` — 미처리 occurrence로 계상 ([calculations.ts:249](src/utils/calculations.ts:249))
- 9월 카드대금 추정치 — 같은 occurrence를 카드 청구에 합산 ([cardPayments.ts:163](src/utils/cardPayments.ts:163))

3.1을 고쳐 카드대금을 고정비에 넣는 순간, 같은 돈을 두 달에 걸쳐 두 번 확보하게 된다. **3.1과 3.5는 반드시 같이 고쳐야 한다.**

### 3.6 수동 입력이 정기 일정과 연결되지 않는다

사용자가 10일 점심에 이체한 뒤 그것을 앱에 직접 입력하면:

- `recurringTemplateId`가 없으므로 → **용돈 사용**에서 780,000원 차감
- 정기 일정은 여전히 미처리 → 고정비 780,000원 계속 예약

같은 돈이 두 번 빠지고, 게다가 잘못된 트랙(용돈)에 들어간다. [AddTransactionModal](src/components/AddTransactionModal.tsx)은 `recurringOccurrences`를 props로 받지만 AI 음성 문맥([LiveVoicePanel.tsx:180](src/components/LiveVoicePanel.tsx:180))으로만 전달하고, 미처리 일정과 매칭하는 로직은 없다.

### 3.7 숫자가 소비와 무관한 이유로 계속 변한다

주기 중간에 아래 중 하나만 일어나도 "남은 용돈"이 바뀐다.

- 정기 항목 금액 수정 → `expectedAmount` 변경 → `totalExpectedFixedExpenses` 변경
- 템플릿의 아무 필드나 수정 → [storage.ts:244](src/utils/storage.ts:244)에서 `expectedAmount`가 `defaultAmount`로 초기화되며 이월 금액 소실
- 카드 사용 추가 → 다음 달 카드대금 추정 변동 (현재는 예산에 미반영이나, 3.1 수정 후에는 반영됨)
- 정기 항목 확정/취소

사용자 입장에서 "어제 남은 돈"과 "오늘 남은 돈"의 차이가 어제 쓴 돈과 일치하지 않는다. 이것이 앱 신뢰를 무너뜨리는 가장 조용하고 치명적인 문제다.

### 3.8 할부가 비대칭으로 계산된다

- **용돈 트랙**: 구매한 주기에 `transaction.amount` 전액 차감 ([calculations.ts:230](src/utils/calculations.ts:230)은 `installment`를 보지 않는다)
- **카드대금 트랙**: `getInstallmentCharge`로 회차분만 계상 ([cardPayments.ts:123](src/utils/cardPayments.ts:123))

12개월 할부 120만원 구매 시 그 달 용돈이 120만원 통째로 사라진다. 할부를 쓰는 이유 자체를 부정하는 계산이다.

## 4. 계산 모델 정의

요구사항에 앞서, 앱 전체가 따라야 할 단일 모델을 먼저 정의한다. 이 절이 이 PRD의 핵심이다.

### 4.1 두 트랙

```
┌─ 현금 트랙 (Cash) ────────── "통장에서 나갈 돈" ─ 급여일에 확정 ─┐
│                                                                 │
│   급여 입금                                      +3,000,000     │
│   − 계좌 고정 이체 (카드 결제 정기지출 제외)        −780,000     │
│   − 이 주기에 결제일이 오는 카드대금                −900,000     │
│   − 저축 목표 (사용자 설정, 선택)                         −0     │
│   ─────────────────────────────────────────────────────────     │
│   = 이번 주기 생활비 (livingBudget)              =1,320,000     │
└─────────────────────────────────────────────────────────────────┘

┌─ 소비 트랙 (Spend) ───────── "내가 쓴 돈" ─ 매일 갱신 ──────────┐
│                                                                 │
│   이번 주기 변동지출 (현금·체크·신용 무관)          300,000     │
│   ※ 할부는 회차분만                                             │
│   ─────────────────────────────────────────────────────────     │
│   남은 생활비 = 1,320,000 − 300,000            =1,020,000       │
│   하루 안전 금액 = 1,020,000 / 남은 29일          =    35,172   │
└─────────────────────────────────────────────────────────────────┘
```

### 4.2 불변식 (테스트로 고정)

| # | 불변식 | 의미 |
|---|---|---|
| INV-1 | **단일 소속** — 모든 금액은 정확히 한 트랙 × 한 주기에만 계상된다 | 카드 결제 정기지출은 고정 이체 합계에 넣지 않는다. 카드대금 안에만 존재한다. |
| INV-2 | **트랙 분리** — 카드 구매는 소비 트랙(사용 주기)에만, 그 청구서는 현금 트랙(결제 주기)에만 | 3.5의 이중 노출 차단 |
| INV-3 | **기간 귀속** — 카드대금은 `결제일이 속한 급여 주기`에 귀속된다 | 달력 월이 아니라 주기 기준. 3.4(a) 해결 |
| INV-4 | **기준선 불변** — 확정된 `livingBudget`은 그 주기 안에서 소비 외의 이유로 변하지 않는다 | 3.7 해결. 변경 시 사용자 승인 필요 |
| INV-5 | **할부 대칭** — 할부 구매는 두 트랙 모두에서 회차분으로 계상된다 | 3.8 해결 |

INV-1과 INV-2는 다음 형태의 속성 테스트로 검증한다.

```
임의의 거래 집합 S에 대해
  Σ(모든 주기의 현금 트랙 유출) == Σ(S의 실제 계좌 유출)
  Σ(모든 주기의 소비 트랙) == Σ(S의 변동지출, 할부는 회차 합)
  두 합계는 서로 겹치는 항목을 갖지 않는다
```

### 4.3 타입 변경

```ts
// 카드 이용기간. 결제일만으로는 어느 사용분이 청구되는지 결정할 수 없다.
interface PaymentCard {
  billingDay?: number | null;           // 기존: 결제일
  statementClosingDay?: number | null;  // 신규: 이용기간 마감일 (없으면 결제일 기준 추정)
}

// 급여일에 확정한 주기 기준선. INV-4의 저장소.
interface CycleBaseline {
  yearMonth: string;              // 급여 주기 라벨
  confirmedIncome: number;
  accountFixedOutflow: number;
  cardSettlement: number;
  savingsReserve: number;
  livingBudget: number;           // 위 네 값의 산출 결과
  lockedAt: string;               // 확정 시각. null이면 미확정(추정 모드)
  supersededBy?: string | null;   // 주기 중 재확정 시 이전 기준선 추적
}

// 카드대금 이체를 거래로 기록해도 소비 트랙에 들어가지 않게 한다.
type TransactionRole = 'normal' | 'card_settlement' | 'transfer';
interface Transaction {
  role?: TransactionRole;         // 기본 'normal'
}
```

`calculateMonthSummary`는 카드 정산 요약과 기준선을 인자로 받도록 확장하고, 기존 필드는 별칭으로 유지해 호출부 회귀를 막는다.

- 확정 금액(`monthlyPaymentAmounts`)이 입력되면 추정치 대신 그 값을 현금 트랙에 쓴다.
- 추정 대비 실제 차액을 기록해 다음 주기 추정 정확도 표시에 사용한다. ("최근 3회 추정 오차 평균 4%")

## 9. 열린 질문

- 저축 목표(`savingsReserve`)를 별도 봉투로 둘 것인가, 생활비 잔여로 둘 것인가. 전자는 강제성이 있고 후자는 유연하다. 초기에는 선택형(기본 0원)으로 두고 사용 패턴을 관찰한다.
- 주기 중 예상치 못한 큰 수입(보너스·환급)이 들어오면 기준선을 자동 갱신할 것인가. P0-3의 변경 알림 대상에 포함하되 기본 동작은 "그대로 두기"로 한다.
- 체크카드를 신용카드와 동일하게 소비 트랙에 넣되 현금 트랙에서는 즉시 유출로 처리해야 한다. 현재 [cardPayments.ts:137](src/utils/cardPayments.ts:137)은 체크카드를 별도 집계만 하고 계좌 잔액에 연결하지 않는다. P2-1 범위에 포함할지 결정 필요.
- 마이너스 통장·비상금 계좌를 별도 봉투로 다룰 것인가. 이번 범위에서는 제외한다.

### 계획 대비 편차

**(1) P1-1의 주기 귀속 부분을 앞당김.** `calculateMonthlyCardSettlementSummary`가 `monthStartDay`를 실제로 사용하도록 수정하고, 카드대금을 결제일이 속한 주기에 귀속시켰다(INV-3). P0-1이 카드대금을 예산에 반영하는 이상, 귀속 주기가 틀리면 반영 전보다 더 나빠지기 때문이다. `MonthlyCardSettlement`에 `usageYearMonth`를 추가해 어느 달 사용분인지 화면에 표기한다.

`PaymentCard.statementClosingDay`와 카드사 프리셋(P1-1의 나머지)은 3차에 그대로 남는다. 이용기간은 여전히 "결제월 직전 달" 가정이다.

**(2) P0-2의 추정 모드 계산 부분을 앞당김.** 미처리 고정지출은 이미 예약하면서 미확정 급여만 배제하는 비대칭이 3.2의 직접 원인이라, 계획 기준 수입(`planningIncome`)을 도입하고 `isProjected`로 표시했다. 대시보드에 "급여 입금 예정 기준" 배지를 붙였다. 급여일 4단계 확정 시트와 `CycleBaseline` 저장은 2차에 그대로 남는다.

`totalIncome`은 실제 입금액만 유지한다. 계획에만 예정 수입을 쓰고 보고에는 쓰지 않는다.

**(3) 용돈 한도 0의 의미 변경.** 기존에는 `totalLimit: 0`이 `spendableLimit = 0`이 되어 신규 사용자가 지출을 기록하는 즉시 사용률 999%·위험 등급이 됐다. 0을 "한도 미설정"으로 해석해 생활비 전액을 사용 가능액으로 둔다.

### 설계 판단

**저축은 강제 봉투가 아닌 선택값으로 둔다.** §9의 열린 질문 중 하나였다. 4단계에서 입력하고 기본값 0이며, 0이면 생활비 전액을 쓴다. 강제 이체까지는 만들지 않았다.

**이월 판정 기준을 "직전 달 대비"로 잡았다.** 계획 단계에서는 템플릿 금액 대비로 적었으나, 그렇게 하면 여름 공과금처럼 몇 달에 걸쳐 완만히 오르는 정상 패턴이 매달 초기화된다. 직전 달을 그 이전 달과 비교해 이상치 한 달만 걸러내면 점진적 상승은 그대로 따라간다. 기존 테스트(90,000 템플릿에 110,000 → 125,000 이월)가 이 구분을 이미 문서화하고 있었다.

**`revisions[]` 인라인 배열을 선택했다.** 계획서의 `supersededBy` 포인터 방식은 주기별 이력을 모으려면 별도 조회가 필요하다. 주기당 개정 횟수가 많지 않아 한 문서에 담는 편이 조회·동기화 모두 단순하다.

## 13. 3차 구현 기록 (위험 항목 + P1-2, P1-3)

### 위험 항목

**수동 카드대금 항목의 명시적 분류.** 기존 `getDuplicateManualCardSettlementTemplateIds`는 이름 패턴 하나로 판정해 조용히 제외했다. 패턴이 좁아 `신한카드`처럼만 지어 둔 항목은 걸리지 않았고, 1차에서 카드대금이 예산에 들어오면서 그런 항목은 **계좌 이체와 카드대금 양쪽에 계상**됐다.

`findManualCardSettlementCandidates`로 재작성하고 판정을 두 단계로 나눴다.

| 상태 | 조건 | 처리 |
|---|---|---|
| `replaced` | 사용자가 확정했거나, 이름에 카드대금 표현 + 카드명/카드사가 함께 있음 | 계좌 이체에서 제외 (기존 동작 유지) |
| `needs_review` | 결제계좌가 일치 + 이름에 "카드" 포함 + 금액이 자동 카드대금과 20% 이내 | **제외하지 않고** 중복 경고로 노출 |

`RecurringTemplate.cardSettlementCardId` / `cardSettlementReviewedAt`을 추가해 사용자의 답을 저장한다. 명시적 결정은 항상 휴리스틱보다 우선한다. `needs_review`를 제외하지 않는 것은 의도적이다 — 조용히 감추면 실제로 별개인 고정지출이 계획에서 사라지므로, 답하기 전까지는 계산에 남기고 경고만 띄운다.

**계산 모델 변경 1회성 안내** (`CashflowModelNotice`). 카드대금이 있는 사용자에게만 1회 노출하고 `UserProfile.cashflowModelNoticeSeenAt`에 기록한다. 이전 계산이 틀렸다는 점을 명시하고, 고정 출금·저축 예정액을 변경 전/후로 대조한 뒤 "줄어든 만큼이 없어진 것은 아니다"를 설명한다.

### P1-2 할부 대칭 (INV-5)

`confirmedVariableExpenses`가 할부를 회차분으로 계상한다. 이를 위해 대상 거래를 이번 주기 거래가 아니라 **회차가 이번 주기에 도래하는 모든 할부 거래 + 이번 주기 비할부 거래**로 바꿨다. 구매한 주기라고 전액을 잡지 않으며, 이전 주기 구매의 회차도 빠지지 않는다.

`getCategoryBreakdown`도 같은 규칙을 쓴다. 월말 예측의 일평균에서는 할부를 제외한다 — 회차는 이미 주기 전체에 확정된 금액이라 일평균에 넣으면 두 번 예측된다.

거래 입력 화면은 총액 대신 **월 부담과 남은 회차**를 보여준다.

**미래 약정 뷰** (`futureCommitments.ts`, `FutureCommitmentsCard`). 앞으로 6주기의 확정 유출을 고정비/할부/카드대금 3구간 스택으로 표시하고, 할부가 끝나는 주기에 "다음 주기부터 매달 N원 여유"를 붙인다. 할부 회차는 카드대금 안에 있으므로 스택에서 분리해 이중 표시를 피한다. 분석 탭 최상단에 배치했다.

### P1-3 정기 ↔ 수동 거래 매칭

`recurringMatch.ts`. 금액 10% 이내 + 예정일 ±5일 + 유형 일치를 통과한 미처리 occurrence를 점수순으로 반환한다. 거래처·카테고리 일치는 비슷한 정기 항목 사이의 순위를 가르는 용도로만 가산한다.

수동 저장 시 후보가 있으면 저장을 막고 `정기 항목으로 확정` / `별개 지출로 저장`을 묻는다. 전자는 occurrence를 확정 처리하고, 후자는 원래대로 저장한다.

### 계획 대비 편차

`needs_review` 판정에 **금액 유사도 조건을 추가**했다. 계획서에는 "결제계좌가 카드 결제계좌와 일치"만 적었으나, 그러면 같은 통장에서 나가는 월세·보험료가 전부 경고에 걸린다. 결제계좌 + "카드" 표현 + 금액 근접 세 조건을 모두 요구해 오탐을 없앴다.

## 14. 4차 구현 기록 (P1-1 완결, P1-5, P1-4)

### P1-1 카드 이용기간 (3차 잔여분)

`PaymentCard.statementClosingDay`를 추가하고, 청구 대상을 달력 월이 아니라 **실제 이용기간**으로 바꿨다. `getCardSettlementSchedule`이 `usageStartDate` / `usageEndDate` / `hasStatementWindow`를 함께 반환하고, `calculateCardPaymentSummary`는 선택적 `usageWindow`로 그 구간을 그대로 집계한다.

마감일 계산은 **결제일 직전의 가장 최근 마감일**을 창의 끝으로 잡는다. 이렇게 하면 마감일이 결제일보다 뒤인 조합(마감 22일 · 결제 5일)도 한 달 뒤로 자동 보정된다. 창의 시작은 그 한 달 전 마감일 다음 날이다.

마감일 미설정 카드는 기존 추정을 유지하되 `hasStatementWindow: false`로 표시하고, 화면에 "이용기간 미설정, 추정"을 병기한다.

카드사 프리셋(`cardIssuerPresets.ts`)은 9개 카드사의 결제일↔마감일 조합을 담는다. 결제일을 고르면 마감일이 자동으로 채워지고 사용자가 덮어쓸 수 있다. **프리셋은 초기값일 뿐이며 실제 청구와 다를 수 있다** — 파일 주석에 명시했고, 급여일 3단계는 항상 실제 고지서 금액을 우선한다.

### P1-5 지출 속도

`MonthSummary`에 `periodProgressPercent`, `projectedDepletionDate`, `projectedShortfallDays`, `requiredDailyPace`를 추가했다. 대시보드는 세 가지를 보여준다.

- `기간 26% 지남 · 생활비 45% 사용 · 빠름` (±10%p로 빠름/적정/여유 구분)
- `지금 속도면 2026-09-02에 생활비가 바닥납니다 (7일 부족)`
- `하루 38,200원으로 줄이면 29일을 채울 수 있습니다`

주기 3일 미만이면 노출하지 않는다. 이미 소진된 경우는 오늘을 소진일로 보고한다.

### P1-4 드릴다운과 봉투 스택 바

급여가 네 갈래(계좌 이체 / 카드대금 / 저축 / 생활비)로 쪼개지는 가로 스택 바를 분해 카드 위에 놓았다. 색은 분해 항목의 스와치와 1:1로 맞췄고, 폭 전환에 `motion-reduce:transition-none`을 적용했다.

계좌 고정 이체와 카드대금은 `AmountBreakdown`으로 탭하면 구성이 열린다. 계좌 이체는 완료/잔여로, 카드대금은 카드별 금액과 이용기간으로 분해된다.

## 15. 5차 구현 기록 (P2-1 ~ P2-4)

### P2-1 카드대금 결제 기록과 추정 정확도

`Transaction.role`(`normal` / `card_settlement` / `transfer`)과 `settlementYearMonth`를 도입했다. `normal`이 아닌 거래는 `confirmedExpenses` · `confirmedVariableExpenses` · `confirmedFixedExpenses`에서 제외되고, `calculateCardPaymentSummary`의 카드 사용액에서도 빠진다. 후자가 없으면 카드대금 결제 자체가 다음 달 카드 사용액으로 잡혀 무한히 재청구된다.

`setCardSettlementPaid`는 납부 완료 시 `tx_card_settlement_{cardId}_{yearMonth}` 거래를 만들고 되돌리면 삭제한다. 결제일·결제계좌·카드가 함께 기록되므로 내역과 타임라인에 실제 출금으로 나타나되 지출 총계는 건드리지 않는다.

`calculateCardSettlementAccuracy`는 과거 6주기의 확정 금액과 그때의 추정치를 비교해 평균 오차율을 낸다.

**계획 대비 편차:** 계획서에는 "연결 계좌 잔액에 반영"이라고 적었으나 **잔액 스냅샷은 건드리지 않았다.** `BankAccount.balance`는 `balanceAsOf`를 가진 사용자 입력 스냅샷이라 앱이 자동으로 깎으면 그 기준일의 의미가 깨지고, 사용자가 직접 갱신할 때 이중 차감이 된다. 대신 정산 거래를 남기고, 잔고 변화는 P2-3 타임라인이 스냅샷 위에서 계산해 보여준다.

### P2-2 주기 마감 리포트

`buildCycleClosingReport`가 이전 주기의 기준선과 실제 소비를 대조한다. 계획 생활비, 실제 사용, 남긴 돈(또는 초과), 상위 3개 카테고리와 직전 주기 대비 증감, 미처리로 남은 정기 항목을 담는다.

새 주기로 넘어와 현재 주기를 보고 있을 때만 대시보드 최상단에 노출한다. 기준선이 없는 주기는 비교 대상이 없으므로 리포트도 없다. 남긴 돈은 1탭으로 이번 주기 저축 목표가 되고, 미처리 항목은 해당 주기로 이동해 정리할 수 있다.

### P2-3 현금흐름 타임라인

`buildCashflowTimeline`이 계좌 잔액 스냅샷을 시작점으로 주기 전체의 일별 잔고를 만든다. 확정 입출금과 미처리 정기 이체, 미납 카드대금을 각자의 날짜에 적용하고, 오늘 이후 구간에만 현재 소비 속도를 얹는다. 카드 구매는 통장에서 나가지 않으므로 제외하고, `card_settlement` 거래는 실제 출금으로 반영한다.

`CashflowTimelineCard`는 이를 인라인 SVG 한 줄로 그린다. 0선을 점선으로 두고 확정 구간은 실선, 추정 구간은 파선으로 구분한다. 마이너스로 내려가는 첫 날짜가 있으면 경고한다. 잔액이 입력되지 않은 계좌만 있으면 선 자체가 의미 없으므로 렌더하지 않는다.

### P2-4 추정치 표기와 안전망 보완

미확정 급여와 추정 카드대금에 점선 밑줄 + 낮은 대비를 적용해 확정값과 구분했다.

미생성 고정비 안전망을 `getScheduledDatesInPeriod`로 교체했다. 기존 구현은 월간 항목만, 그것도 `holidayPolicy`를 무시하고 계산했다. 이제 **주간 항목은 주기 안 발생 횟수만큼** 예약하고, 두 회계 월을 모두 훑어 휴일 정책이 적용된 날짜를 주기 경계로 다시 거른다.

### 검증

전체 **163개 테스트 통과**, `tsc --noEmit` 및 프로덕션 빌드 정상. 신규 16개:

| 그룹 | 검증 내용 |
|---|---|
| 타임라인 (10) | 주기 전 일자 포함, 이동 없으면 평탄, 카드 결제일 하락, 마이너스 첫날 감지, 카드 구매는 출금 아님, 정산 거래는 출금, 오늘 이후만 추세 적용, 미처리 정기 이체 반영, 잔액 미입력 감지, 납부 완료 청구는 제외 |
| 안전망 (4) | 주간 항목 4회 예약, 휴일 정책 적용, 주기 밖 날짜 제외, 카드 결제 주간 항목 분리 |
| 정산 거래 (2) | 생활비·지출 총계에서 제외, 카드 사용액으로 재청구되지 않음 |

PRD의 5개 릴리스 단계와 위험 항목이 모두 반영됐다. §6 성공 지표 기준:
