# ExpendBreak 운영 안정화 및 데이터 보호 PRD

- 문서 상태: Draft v1.1
- 작성일: 2026-08-10
- 대상: Google AI Studio에서 작성·배포 중인 ExpendBreak
- 전제: Firestore에 실제 운영 데이터가 존재하며, 무중단·무손실 전환이 최우선이다.
- 분석 범위: 현재 저장소의 클라이언트, Express/Gemini API, Firestore 동기화 및 보안 규칙에 대한 정적 분석

## 1. 요약

현재 앱은 가계 거래, 예산, 정기 수입·지출, 계좌·카드, AI 분류·리포트까지 핵심 기능을 빠르게 구성한 단일 사용자용 제품이다. 다만 운영 서비스 관점에서는 데이터 보호와 일관성 계층이 부족하다.

가장 시급한 문제는 다음과 같다.

1. 저장소에 포함된 Firestore 규칙은 모든 문서의 익명 읽기·쓰기를 허용한다.
2. PIN, 계좌번호, 잔액, 거래 내역이 사용자별 경로가 아닌 전역 컬렉션에 저장된다.
3. 새 브라우저에서 로컬 기본값이 클라우드 운영 데이터보다 먼저 저장되어 기존 설정을 덮어쓸 수 있다.
4. 화면에서는 저장 성공처럼 보이지만 Firestore 쓰기 실패가 사용자에게 전달되지 않는다.
5. 전체 초기화는 비동기 삭제와 즉시 재초기화가 경합하고, 백업·재인증·완료 검증이 없다.
6. 정기 항목 생성은 시작·종료일, 주기, 휴일 정책을 적용하지 않으며 여러 기기에서 중복 거래가 만들어질 수 있다.
7. AI 사용 설정과 동의 정보는 실제 AI 호출을 차단하지 않고, AI 출력도 런타임 검증 없이 거래 데이터가 될 수 있다.

따라서 첫 번째 릴리스 목표는 신규 기능 추가가 아니라 **운영 데이터의 소유권, 백업, 원자적 저장, 복구 가능성**을 확보하는 것이다.

### 확정된 제품 방향

- 앱은 **1인 전용**으로 운영하며 사용자 초대와 가계 공유는 지원하지 않는다.
- 첫 화면은 PIN 로그인 화면이며, **PIN 검증이 성공하기 전에는 Firestore 초기화·조회·실시간 리스너 등록을 시작하지 않는다.**
- PIN은 Firestore나 브라우저 저장소에 평문으로 저장하지 않는다. 서버가 PIN을 검증하고 고정 소유자 UID의 짧은 세션 또는 Firebase custom token을 발급한다.
- 계좌 잔액은 거래 내역으로 자동 계산하지 않고 사용자가 직접 갱신하는 수동 스냅샷으로 관리한다.
- 계좌번호는 PIN 로그인 후 전체 값을 기본 표시하며 송금 편의를 위해 원터치 복사를 제공한다.
- 기능 확장보다 반복 입력, 정기 송금 확인, 복사, 수정, 실행 취소 같은 일상 UI/UX의 마찰을 줄이는 데 우선순위를 둔다.

## 2. 현재 제품과 사용자 흐름

### 제공 기능

- 월별 수입·지출 대시보드와 예산 상태
- 수동 및 Gemini 기반 자연어 거래 등록
- 거래 검색·필터·수정·삭제
- 월 용돈 한도
- 정기 수입·지출 템플릿과 예정 건 처리
- 은행 계좌·결제 카드 관리
- 월별 분석 차트와 AI 절약 리포트
- CSV 내보내기 및 전체 초기화
- 앱 PIN 및 서버 `APP_ACCESS_KEY` 기반 잠금

### 현재 데이터 흐름

1. 앱이 시작되면 Firestore 실시간 리스너를 등록한다.
2. 동시에 `localStorage`가 비어 있으면 기본 프로필, 카테고리, 예산 등을 생성한다.
3. 일부 기본값은 Firestore로 즉시 전송된다.
4. 사용자의 변경은 먼저 `localStorage`에 반영되고 Firestore 쓰기는 기다리지 않은 채 실행된다.
5. Firestore 스냅샷이 도착하면 컬렉션 전체를 다시 `localStorage`에 덮어쓴다.

이 구조는 빠른 프로토타입에는 적합하지만 운영 환경에서는 초기화 경합, 저장 실패 은닉, 여러 기기 간 덮어쓰기 문제를 만든다.

## 4. 제품 목표

### 목표

1. 인증되지 않은 사용자는 어떤 금융 데이터도 읽거나 쓸 수 없다.
2. 기존 운영 문서의 ID, 금액, 날짜, 생성 시각을 보존하며 사용자별 데이터 경로로 이관한다.

6. 삭제·초기화·마이그레이션은 백업, 미리보기, 재인증, 감사 기록, 롤백을 제공한다.

- 이번 단계에서의 다중 통화 정산
- 디자인 전면 개편
- 운영 데이터의 일괄 정리 또는 과거 기록 재분류

2. PIN 입력 전에는 Firestore 네트워크 요청과 로컬 운영 데이터 표시가 발생하지 않는다.

8. AI 기능을 끄면 어떠한 금융 문장·요약도 AI API로 전송되지 않는다.
9. 삭제한 거래는 보관함에서 일정 기간 복원할 수 있다.

## 6. 기능 요구사항

### FR-01 1인 PIN 로그인 및 데이터 로드 게이트

- 앱은 단일 고정 소유자 UID(예: `owner`)만 사용하고 가입, 사용자 초대, 계정 전환 UI를 제공하지 않는다.
- 초기 화면에서는 PIN 입력 UI와 인증에 필요한 최소 API만 활성화한다.
- 클라이언트는 PIN을 HTTPS로 서버에 제출하고, 서버는 Secret Manager 또는 환경변수에 보관된 salted hash와 constant-time 방식으로 검증한다.
- 검증 성공 시 서버는 고정 소유자 UID에 대한 Firebase custom token을 발급하고 클라이언트는 `signInWithCustomToken`으로 인증한다.
- Firebase Auth 지속성은 브라우저 세션 범위로 제한하고, 명시적 잠금·유휴 잠금 시 `signOut`과 리스너 해제를 함께 수행한다.
- Firestore 초기화, 로컬 캐시 복호화/표시, 스냅샷 리스너 등록은 유효한 세션 확인 뒤에만 수행한다.
- 데이터 경로는 `users/{ownerUid}/...`로 고정하고 Firestore 규칙은 해당 인증 UID만 허용한다.
- 계좌, 카드, 거래, 예산, 정기 항목, 설정 모두 동일한 소유자 경로와 정책을 따른다.
- PIN 원문은 Firestore, `localStorage`, `sessionStorage`, 로그, 분석 이벤트에 저장하지 않는다.
- 연속 실패에 지수형 대기, 요청 속도 제한, 실패 횟수 초기화 정책을 적용하되 영구 계정 잠금으로 소유자가 앱을 잃지 않도록 한다.
- 기본 PIN `1234`는 제거하고 최초 배포 시 운영 secret을 명시적으로 설정하지 않으면 앱을 시작하지 않는다.
- 잠금 버튼과 선택 가능한 유휴 자동 잠금을 제공한다. 자동 잠금 시 화면 상태와 민감 캐시를 숨기고 Firestore 리스너를 해제한다.
- API는 PIN 문자열이 아니라 발급된 인증 토큰을 검증한다.
- Firebase 웹 API 키 자체는 공개 구성을 전제로 하되 보안은 Auth, Rules, App Check로 구현한다.

### FR-02 클라우드 정본 저장소

- Firestore를 정본으로 하고 `localStorage`는 버전이 있는 읽기 캐시 또는 오프라인 큐로만 사용한다.
- 최초 부팅은 `PIN 화면 → 서버 검증 → 소유자 토큰 발급 → Firestore 초기화 → 클라우드 hydrate 완료 → 앱 공개` 순서를 따른다.
- 초기 샘플은 서버가 “신규 사용자이며 데이터 0건”임을 확인한 뒤 사용자 동의로만 생성한다.
- 저장 API는 성공을 기다린 후 완료 상태를 표시한다.
- 실패 시 `동기화 대기/실패/재시도` 상태를 제공한다.
- 문서에 `schemaVersion`, `ownerUid`, 서버 생성 `createdAt/updatedAt`, 필요 시 `revision`을 둔다.
- 여러 문서를 함께 바꾸는 작업은 Firestore transaction 또는 idempotent backend command로 처리한다.

### FR-03 무손실 마이그레이션

- 이관 전 Firestore 관리 백업과 컬렉션별 JSON/CSV 논리 백업을 모두 만든다.
- 문서 수, 거래 금액 합계, 월별 합계, 고유 ID 집합을 이관 전후 비교한다.
- 기존 루트 컬렉션은 이관 기간 동안 읽기 전용으로 유지한다.
- 이관 작업은 동일 문서 ID로 반복 실행해도 결과가 같은 idempotent 작업이어야 한다.
- `migrationVersion` 및 실행자, 시작·완료 시각, 카운트, 오류를 별도 감사 문서에 남긴다.
- 이관 전 `transaction.type/category.type`, `template.type/category.type`, merchant rule/category 관계가 맞지 않는 문서를 별도 보고서로 추출한다.
- 기존 불일치 데이터는 자동으로 수입·지출 유형을 뒤집지 않는다. 원래 금액과 `type`은 보존하고 사용자 확인 후 호환되는 카테고리로 매핑한다.
- 사용자가 판단하기 전까지 불일치 카테고리는 유형별 `미분류 수입` 또는 `미분류 지출` 임시 버킷으로 표시하되 원본 category ID를 감사 필드에 보존한다.
- 데이터 삭제는 이관 검증 및 안정화 기간이 끝난 후 별도 승인으로 수행한다.

### FR-04 백업, 삭제 및 복구

- 거래와 주요 설정은 즉시 물리 삭제하지 않고 `deletedAt/deletedBy`를 기록한 소프트 삭제를 기본으로 한다.
- 거래 삭제 직후 실행 취소를 제공한다.
- 전체 초기화 전 다음을 요구한다: 최근 백업 확인, 계정 재인증, 대상 건수 미리보기, 확인 문구 직접 입력.
- 초기화는 백엔드 작업으로 실행하고 진행률과 최종 삭제 건수를 보여준다.
- 실패 시 중단 지점부터 재개할 수 있어야 한다.
- `localStorage.clear()`를 사용하지 않고 앱 전용 키만 제거한다.

### FR-05 정기 거래 엔진

- 월간·주간 주기, 시작일, 종료일, 말일 보정, 휴일 정책을 실제 일정 생성에 적용한다.
- 자동 처리와 단순 예정 표시를 구분된 용어로 제공한다.
- 발생 건 문서 ID를 `templateId + scheduledDate` 기반의 결정적 ID로 만들어 중복 생성을 차단한다.
- 발생 건 확정과 거래 생성은 한 트랜잭션으로 수행한다.
- 생성된 거래에는 occurrence ID를 유일 참조로 저장하고 중복을 거부한다.
- 연결 거래 삭제 시 발생 건을 `needs_confirmation`으로 복구하거나 사용자에게 관계 처리 방식을 묻는다.
- 템플릿 및 결제수단 삭제 전 참조 건수를 표시하고 안전한 대체·보관 정책을 제공한다.

### FR-06 AI 사용 통제 및 출력 검증

- `aiClassificationEnabled=false`이면 AI 입력 모드와 분류 API 호출을 모두 차단한다.
- `aiInsightsEnabled=false`이면 분석 화면에서 AI 리포트 호출을 수행하지 않는다.
- 최초 AI 사용 시 전송 항목, 목적, 보관 여부를 알리고 명시적 동의를 저장한다.
- 서버는 요청 길이, 배열 크기, 허용 필드, 금액 범위, 날짜 형식, 카테고리 소유권을 검증한다.
- 모델 출력은 런타임 스키마로 검증하고 존재하는 카테고리 ID만 허용한다.
- 잘못된 출력은 거래로 저장하지 않고 안전한 수동 확인 상태로 전환한다.
- 사용자별 쿼터, 속도 제한, 타임아웃, 오류 코드, 요청 ID를 적용한다.
- AI 리포트 캐시 키는 월뿐 아니라 거래·예산 데이터 버전 또는 해시를 포함한다.

### FR-07 수입·지출 유형과 카테고리 무결성

- `Transaction.type`, `RecurringTemplate.type`, `Category.type`의 관계를 도메인 불변식으로 정의한다.
- 거래와 정기 템플릿은 반드시 `entity.type === selectedCategory.type`인 경우에만 저장할 수 있다.
- UI뿐 아니라 저장소 계층과 백엔드 명령에서도 같은 검증을 수행하여 우회 저장을 차단한다.
- 신규 폼의 기본 카테고리는 배열 첫 항목이 아니라 `getDefaultCategory(type)`으로 결정한다. 기본값은 지출 `etc_expense`, 수입 `etc_income`으로 한다.
- 유형을 변경하면 현재 카테고리가 호환되는지 검사하고, 호환되지 않으면 해당 유형의 최근 사용 카테고리 또는 기본 기타 카테고리로 즉시 바꾼다.
- 카테고리 선택 목록에는 현재 유형과 일치하는 활성 카테고리만 보여준다.
- 카테고리 병합은 같은 유형끼리만 허용한다.
- merchant rule은 적용 대상 거래 유형을 함께 저장하거나, 분류 결과 유형과 카테고리 유형이 다르면 적용하지 않는다.
- AI 결과는 반환 category ID의 실제 카테고리 유형까지 검증하고 불일치하면 사용자 확인 전 저장하지 않는다.
- 정기 발생 건에는 생성 당시 `typeSnapshot`, `categoryIdSnapshot`, `templateRevision`을 저장하여 템플릿 수정이 과거·기존 발생 건을 암묵적으로 재분류하지 않게 한다.
- 템플릿 유형 또는 카테고리를 수정할 때 `이번 건만/아직 처리하지 않은 건부터/다음 달부터` 적용 범위를 선택하게 한다.

### FR-08 정확한 재무 계산

- 총 수입·지출의 정본 기준은 `Transaction.type`으로 통일하고 카테고리는 세부 분류 차원으로만 사용한다.
- 수입·지출 카테고리가 맞지 않는 기존 거래는 반대편 카테고리 합계에 넣지 않고 `분류 확인 필요`로 별도 표시한다.
- 모든 카테고리 합계와 미분류 합계의 합은 해당 유형의 총액과 정확히 일치해야 한다.
- 예정 수입·지출은 유효한 템플릿 또는 발생 건의 `typeSnapshot`이 있을 때만 집계한다. 템플릿을 찾지 못한 발생 건을 임의로 지출 처리하지 않는다.
- 저장된 예산 `thresholds`를 경보 계산에 사용한다.
- “최근 14일 평균”은 실제 최근 14일의 변동 지출만 사용한다.
- 미래 날짜 거래와 데이터가 없는 날을 어떻게 처리하는지 계산 규칙을 명문화한다.
- 사용자 시간대와 월 시작일 설정을 모든 월 집계에 적용한다.
- 계좌 잔액은 거래와 자동 연동하지 않는 **수동 스냅샷**으로 확정하고 `balance`, `balanceAsOf`, `balanceUpdatedAt`을 저장한다.
- 잔액 화면에는 “직접 입력 잔액”과 기준 날짜를 함께 표시하여 실제 은행 잔액과 자동 동기화된다는 오해를 막는다.
- 잔액 수정은 계좌 카드에서 바로 실행하고 저장 직후 이전 값으로 되돌릴 수 있는 실행 취소를 제공한다.
- 날짜 변경 시 `localDate`와 정렬용 시각을 함께 일관되게 갱신한다.

### FR-09 운영 가시성 및 품질 게이트

- 인증 실패, Firestore 읽기·쓰기 실패, AI 실패, 마이그레이션 오류를 구조화 로그와 오류 추적 도구에 기록한다.
- 화면에 마지막 동기화 시각과 현재 동기화 상태를 표시한다.
- 거래 목록은 월/기간 쿼리와 페이지네이션으로 가져온다.
- 단위 테스트, Firestore emulator 통합 테스트, 핵심 E2E 테스트를 CI에서 실행한다.
- 배포는 dev/staging/prod 환경과 Firebase 프로젝트를 분리한다.
- 서버는 플랫폼 `PORT`를 사용하고 서버 번들·소스맵을 정적 파일 경로 밖에 둔다.

## 7. UI/UX 편의 요구사항

### UX-01 PIN 로그인과 잠금

- PIN 입력 화면은 숫자 키패드에 최적화하고 모바일에서 숫자 키보드를 자동 호출한다.
- PIN 길이가 충족되면 자동 제출하되 중복 제출을 막고, 로딩 중에는 입력값을 노출하지 않는다.
- 실패 시 “PIN 오류”, “네트워크 오류”, “일시 제한”을 구분해 다음 행동을 안내한다.
- 로그인 성공 직후 빈 대시보드를 먼저 보이지 않고 데이터 로딩 skeleton과 단계별 상태를 표시한다.
- 헤더에 즉시 잠금 버튼을 두고, 유휴 자동 잠금 시간은 `사용 안 함/5분/15분/30분` 중 선택하게 한다.
- 새로고침 시 유효 세션이 남아 있으면 다시 PIN을 요구할지 여부를 “브라우저를 닫을 때까지 유지” 설정으로 제어한다.

### UX-02 계좌번호 확인과 복사

- PIN 로그인 이후 계좌번호는 마스킹 없이 전체 표시한다.
- 계좌 카드의 계좌번호 영역 전체와 별도 복사 아이콘을 모두 클릭 가능한 대상으로 제공한다.
- 복사 성공 시 “국민은행 생활비 통장 계좌번호를 복사했습니다”처럼 대상을 포함한 toast와 햅틱 피드백을 제공한다.
- `계좌번호만 복사`와 `은행명 + 계좌번호 + 예금주 복사` 두 동작을 제공한다.
- 복사 문자열은 불필요한 장식 문자를 제외하고 송금 앱에서 바로 사용할 수 있게 한다.
- 정기 송금 화면에서도 계좌 상세 화면으로 이동하지 않고 계좌번호와 전체 송금 정보를 바로 복사할 수 있어야 한다.
- 여러 정기 송금 건은 `은행 / 계좌번호 / 예금주 / 금액 / 메모` 형식으로 한 번에 복사하는 기능을 제공한다.
- Clipboard API 실패 시 계좌번호가 선택된 상태와 수동 복사 안내를 제공한다.
- 로그인 전, 잠금 상태, 앱 전환 미리보기에서는 계좌번호와 잔액이 보이지 않도록 민감 화면을 가린다.

### UX-03 수동 계좌 잔액 관리

- 계좌 카드에는 `직접 입력 잔액`, `기준일`, `마지막 수정`을 함께 표시한다.
- 잔액 숫자를 누르면 별도 관리 화면을 거치지 않고 빠른 수정 sheet를 연다.
- 입력 중 천 단위 구분과 한글 금액 미리보기(예: `1,250,000원 · 125만원`)를 제공한다.
- `+1만`, `+5만`, `-1만`, `-5만` 빠른 조정과 `현재 잔액으로 덮어쓰기`를 제공한다.
- 저장 후 5초 동안 실행 취소를 제공하고 잔액 변경 이력을 최소한 최근 항목까지 확인할 수 있게 한다.
- 거래 등록 후 계좌 잔액을 자동으로 증감하지 않는다. 대신 필요하면 “이 계좌 잔액도 직접 수정” 바로가기를 노출한다.
- 여러 계좌 합계에는 “직접 입력 잔액 합계”라는 라벨과 가장 오래된 기준일을 표시한다.

### UX-04 빠른 거래 입력

- 기본 입력 모드는 마지막 사용 모드를 기억하되 AI가 꺼져 있으면 수동 입력으로 고정한다.
- 수입·지출 유형을 먼저 선택하게 하고 카테고리 목록은 선택 유형과 일치하는 항목만 표시한다.
- 유형 변경으로 카테고리가 자동 변경되면 `지출 유형에 맞춰 기타 지출로 변경했습니다`라는 짧은 안내를 표시한다.
- 수입은 초록, 지출은 붉은색과 `수입/지출` 텍스트 배지를 함께 사용해 색상만으로 구분하지 않는다.
- 금액 입력은 숫자 키패드, 천 단위 구분, 한글 금액 미리보기, 자주 쓰는 금액 버튼을 제공한다.
- 최근 사용처, 최근 카테고리, 마지막 결제수단을 제안하되 저장 전에 모두 수정할 수 있게 한다.
- 동일 날짜·금액·사용처의 최근 거래가 있으면 중복 가능성을 경고한다.
- 저장 후 modal을 즉시 닫고 toast에서 `내역 보기`와 `실행 취소`를 제공한다.
- 연속 입력 사용자를 위해 `저장 후 하나 더 입력` 선택지를 제공한다.
- 필수값 오류는 `alert()` 대신 해당 필드 아래에 표시하고 첫 오류 필드로 포커스를 이동한다.

### UX-05 정기 송금·결제 체크리스트

- 기본 화면은 `기한 지남`, `오늘`, `이번 주`, `이후` 순으로 묶고 미처리 건만 우선 노출한다.
- 정기 항목 등록은 `고정 수입/고정 지출`을 먼저 고르게 하고, 카테고리는 해당 유형만 노출한다.
- 저장 버튼 위에 `고정 지출 · 주거/관리비 · 매월 25일 · 380,000원` 형식의 한 줄 요약을 제공한다.
- 유형과 카테고리가 다른 기존 항목에는 `분류 확인 필요` 배지를 표시하고 한 번에 호환 카테고리를 선택할 수 있게 한다.
- 각 건에서 금액, 은행, 전체 계좌번호, 예금주, 예정일, 상태를 한 화면에 표시한다.
- `계좌번호 복사`, `송금정보 전체 복사`, `처리 완료`를 한 손으로 누를 수 있는 주요 액션으로 배치한다.
- 복사 후 해당 건을 자동 완료 처리하지 않는다. 사용자가 실제 송금을 확인한 뒤 명시적으로 완료한다.
- 완료 처리 후 거래 생성 결과와 실행 취소를 제공한다.
- 동일 은행 또는 동일 계좌별 묶음 보기와 남은 총액을 제공한다.
- 말일 보정이나 휴일 이동이 적용된 경우 원래 예정일과 변경 이유를 함께 표시한다.

### UX-06 조회·수정·복구

- 사용자가 마지막으로 보던 월, 필터, 정렬을 세션 동안 유지한다.
- 거래 검색은 사용처, 메모, 카테고리뿐 아니라 금액과 날짜 범위도 지원한다.
- 거래 수정 화면에서 날짜·금액·카테고리·결제수단을 한 번에 바꿀 수 있게 한다.
- 거래 유형을 바꾸면 카테고리 선택을 같은 유형으로 제한하고 변경 내용을 저장 전 요약한다.
- 설정에 `분류 점검` 화면을 두어 유형·카테고리가 맞지 않는 기존 거래와 정기 항목을 건수·금액별로 검토할 수 있게 한다.
- `분류 점검`에서는 자동 수정 전에 변경 전후 카테고리와 월별 합계 영향 미리보기를 제공한다.
- 삭제는 즉시 사라지게 하되 toast 실행 취소와 휴지통 복원을 제공한다.
- 대량 작업은 선택 개수, 예상 영향, 완료·실패 건수를 명확히 보여준다.
- 빈 화면은 단순 “데이터 없음” 대신 `거래 추가`, `정기 항목 만들기`, `계좌 등록` 중 관련 다음 행동을 제시한다.

### UX-07 상태 피드백과 접근성

- 헤더 또는 설정에 `동기화됨/대기/오류`, 마지막 동기화 시각, 재시도 동작을 제공한다.
- 저장 버튼은 중복 클릭을 막고 진행 상태를 표시하며, 성공 toast는 실제 Firestore 확인 후 노출한다.
- 네트워크가 끊기면 읽기 가능한 범위와 저장 대기 상태를 명확히 구분한다.
- 모바일 터치 대상은 충분한 크기를 확보하고 색상만으로 수입·지출·위험 상태를 구분하지 않는다.
- 복사, 저장, 삭제, 잠금은 스크린리더용 명확한 레이블과 키보드 포커스를 제공한다.
- 계좌번호는 가독성을 위해 화면에서는 하이픈 형식을 유지하되 복사 형식은 사용자가 선택할 수 있게 한다.

### UI/UX 우선순위

| 순위 | 개선 | 기대 효과 |
|---|---|---|
| 1 | PIN 성공 후 데이터 로드 및 명확한 로딩·오류 상태 | 보안과 첫 화면 신뢰 확보 |
| 2 | 계좌번호·송금정보 원터치 복사 | 반복 송금 시간과 오입력 감소 |
| 3 | 정기 송금 체크리스트와 완료 실행 취소 | 가장 빈번한 월간 작업 단축 |
| 4 | 수동 잔액 빠른 수정과 기준일 표시 | 잔액 관리 의미를 명확히 하고 입력 부담 감소 |
| 5 | 거래 저장 실행 취소·연속 입력·최근값 제안 | 일상 기록 속도 향상 |
| 6 | 동기화 상태와 실패 재시도 | 저장 불안과 유령 저장 방지 |
| 7 | 검색·필터 유지와 휴지통 | 반복 조회와 실수 복구 개선 |

## 8. 비기능 요구사항

- 데이터 무결성: 이관 전후 문서 누락 0건, 금액 합계 차이 0원
- 분류 무결성: 신규 저장 데이터의 유형·카테고리 불일치 0건, 유형별 총액과 카테고리 합계 차이 0원
- 보안: PIN 세션이 없는 Firestore 접근 100% 거부, 고정 소유자 UID 외 접근 100% 거부
- 중복 방지: 동일 occurrence에 연결된 활성 거래 최대 1건
- 복구: 사용자 삭제 데이터는 정책상 정한 보관 기간 내 복원 가능
- 동기화: 저장 실패가 성공으로 표시되는 경우 0건
- 성능: 최근 월 대시보드의 초기 데이터 로드를 전체 이력 크기와 분리
- 접근성: 핵심 입력·저장·삭제 흐름을 키보드와 스크린리더로 수행 가능
- 개인정보: AI 비활성 상태의 AI API 요청 0건

## 9. 출시 및 데이터 이관 계획

### Phase 0 — 동결·감사·백업

1. 운영 Firebase 콘솔에서 실제 배포 규칙, 인증 설정, 컬렉션 목록, 데이터 규모를 확인한다.
2. 위험 작업 전 신규 스키마 변경과 전체 초기화 사용을 일시 중지한다.
3. 관리 백업과 논리 백업을 생성하고 별도 위치에 보관한다.
4. 기준 지표를 저장한다: 컬렉션별 건수, 월별 수입·지출 합계, 문서 ID 목록, 최근 updatedAt.
5. 현재 배포 버전과 Git 커밋을 태그한다.

출시 게이트: 백업 복원 리허설 성공 전에는 데이터 경로와 규칙을 변경하지 않는다.

### Phase 1 — PIN 세션과 호환 클라이언트

1. 서버에서 PIN hash를 검증하고 고정 소유자 UID의 짧은 Firebase custom token 또는 HttpOnly 세션을 발급한다.
2. 앱 시작 시 데이터 계층을 초기화하지 않고 PIN 성공 이벤트 뒤에만 Firebase와 로컬 민감 캐시를 연다.
3. 기존 루트와 신규 소유자 경로를 모두 읽을 수 있는 이관 전용 버전을 배포한다.
4. 신규 쓰기는 feature flag로 제어하고 초기에는 기존 경로를 유지한다.
5. 동기화 상태와 오류 UI를 먼저 배포한다.

출시 게이트: PIN 성공 전 Firestore 요청 0건, 올바른 PIN 로그인, 잘못된 PIN 지연, 잠금, 새 기기 복원, 권한 오류 표시가 staging에서 통과해야 한다.

### Phase 2 — 데이터 복사 및 검증

1. 서버 권한의 일회성 마이그레이션 도구로 루트 문서를 `users/{ownerUid}` 아래 동일 ID로 복사한다.
2. 누락 필드는 읽기 호환 기본값으로 보강하되 원본을 수정하지 않는다.
3. 문서 수, ID 집합, 월별·전체 금액 합계를 자동 비교한다.
4. 불일치 보고서가 0건이 될 때까지 신규 경로 쓰기를 열지 않는다.

출시 게이트: 문서 누락 0건, 합계 차이 0원, 참조 무결성 오류 0건.

### Phase 3 — 신규 경로 전환 및 규칙 강화

1. 유효한 PIN 세션으로 발급된 고정 소유자 UID에 한해 신규 경로 읽기·쓰기를 활성화한다.
2. 기존 경로는 읽기 전용 fallback으로 유지한다.
3. 짧은 관찰 기간 동안 신규·기존 경로의 계산 결과를 shadow compare한다.
4. 이상이 없으면 Firestore 규칙을 인증·소유권 기반으로 강화한다.
5. App Check와 API 토큰 검증을 활성화한다.

중요: 현재 규칙을 먼저 닫으면 인증이 없는 기존 앱이 즉시 중단된다. 인증 가능한 클라이언트를 먼저 배포한 뒤 규칙을 전환해야 한다.

### Phase 4 — 정합성·복구·AI 개선

1. 원자적 거래/정기 발생 건 처리와 결정적 ID를 도입한다.
2. 소프트 삭제, 휴지통, 백업 기반 전체 초기화를 적용한다.
3. AI 동의·토글 강제, 서버 입력/출력 검증, 쿼터를 적용한다.
4. 페이지 쿼리, 테스트, 관측성을 배포한다.

### 롤백 전략

- 모든 단계는 원본 루트 컬렉션을 수정하지 않는 복사 방식으로 시작한다.
- 클라이언트의 `dataRootVersion` feature flag로 신규 경로를 즉시 비활성화할 수 있게 한다.
- 신규 경로 장애 시 기존 경로를 읽기 전용으로 열어 조회 기능을 유지한다.
- 쓰기 롤백이 필요한 경우 장애 기간의 신규 변경분을 감사 로그에서 추출해 재적용한다.
- 원본 데이터 삭제는 안정화 및 별도 승인 전까지 금지한다.

## 11. 수용 기준

1. PIN 화면이 표시된 동안 Firestore 초기화, 읽기, 쓰기, 실시간 리스너 요청이 0건이다.
2. 올바른 PIN 검증 후에만 고정 소유자 세션이 발급되고 기존 운영 데이터가 로드된다.
3. PIN 원문이 Firestore, Web Storage, 쿠키의 JavaScript 접근 영역, 로그에 남지 않는다.
4. 연속된 잘못된 PIN 요청은 점진적으로 지연되고, 정상 PIN으로 소유자가 다시 접근할 수 있다.
5. 세션이 없는 사용자가 Firestore REST/SDK로 모든 대상 컬렉션을 읽거나 쓰려 하면 거부된다.
6. 고정 소유자 UID 외 토큰으로 소유자 데이터 경로에 접근하면 거부된다.
7. 캐시가 없는 새 브라우저에서 로그인해도 기존 프로필, 카테고리, 예산이 기본값으로 변하지 않는다.
8. 로그인 후 계좌번호 전체가 표시되고 계좌번호 단독 및 전체 송금정보 복사가 각각 한 번의 동작으로 성공한다.
9. 잔액 변경은 거래 금액과 무관하게 수동으로만 일어나며 기준일과 마지막 수정 시각이 저장된다.
10. 신규 고정 지출 폼의 최초 카테고리는 지출 카테고리이며 수입 카테고리를 저장할 수 없다.
11. 신규 고정 수입 폼에서는 지출 카테고리를 선택하거나 저장할 수 없다.
12. 거래·정기 항목의 유형을 바꾸면 카테고리가 같은 유형의 값으로 보정되고 사용자에게 안내된다.
13. AI 응답, 거래 수정, 카테고리 병합을 포함한 모든 저장 경로에서 유형·카테고리 불일치가 거부된다.
14. 각 월의 지출 카테고리 합계와 `분류 확인 필요` 금액의 합이 총 지출과 정확히 일치하고, 수입도 같은 조건을 만족한다.
15. 템플릿을 찾지 못한 발생 건은 예정 지출로 임의 계산되지 않고 분류 점검 목록에 나타난다.
16. 기존 불일치 데이터의 정리 전후 금액, 유형, 월별 총액이 바뀌지 않고 category ID 변경 이력이 남는다.
17. 네트워크를 끊고 저장하면 “동기화 대기”가 표시되며 재연결 후 문서가 한 번만 생성된다.
18. 같은 정기 발생 건을 두 기기에서 동시에 확정해도 거래는 정확히 하나다.
19. 2월의 30·31일 정기 항목은 정의된 말일 정책에 따라 유효한 날짜가 된다.
20. 거래 삭제 후 연결된 정기 발생 건의 상태가 정책대로 복원된다.
21. AI 분류 또는 AI 인사이트를 끄면 해당 API 네트워크 요청이 발생하지 않는다.
22. 조작된 AI 응답이 존재하지 않는 카테고리나 잘못된 날짜를 포함하면 저장이 차단된다.
23. 전체 초기화는 백업·PIN 재인증 없이는 실행되지 않으며, 실패 후 재개 또는 복원이 가능하다.
24. 이관 검증 보고서의 문서 누락은 0건이고 모든 월별 수입·지출 합계 차이는 0원이다.
25. 권한 거부, 네트워크 실패, AI 실패가 사용자 메시지와 운영 로그 양쪽에 남는다.

## 12. 테스트 전략

- 단위 테스트: 유형별 기본 카테고리, 유형 변경 보정, 카테고리 합계 보존, 날짜 보정, 예산 경보, 최근 14일 예측, AI 스키마 검증
- 속성 기반 테스트: 임의 월/윤년/말일에 대해 항상 유효한 정기 날짜 생성
- Emulator 통합 테스트: PIN 성공 전 접근 거부, 고정 소유자 규칙, 유형·카테고리 불일치 저장 거부, 원자적 확정, 중복 요청, 오프라인 재시도
- 마이그레이션 테스트: 운영 데이터의 익명화 복제본으로 반복 실행·중단·재개·롤백 검증
- E2E 테스트: PIN 전 네트워크 차단, PIN 로그인·잠금, 신규 기기 복원, 계좌번호 복사, 수동 잔액 수정, 지출·수입별 카테고리 제한, 기존 분류 점검, 거래 저장, 정기 확정, 삭제 복원, AI opt-out
- 부하 테스트: 다년 거래 이력과 대량 발생 건에서 월 화면이 전체 컬렉션을 읽지 않는지 확인

## 13. 확정 결정 및 남은 의사결정

### 확정

1. 1인 전용으로 운영하고 공유·초대 기능은 만들지 않는다.
2. PIN 검증 후에만 정보를 로드한다.
3. 계좌번호는 로그인 후 전체 표시하고 복사 편의 기능을 제공한다.
4. 계좌 잔액은 거래와 자동 연동하지 않는 수동 스냅샷으로 유지한다.
5. UI/UX 편의 개선을 기능 확장보다 우선한다.

### 남은 의사결정

1. PIN 길이 정책과 세션 유지 시간의 기본값
2. 삭제 데이터 보관 기간과 백업 보존 기간
3. `auto`가 실제 자동 등록을 뜻하는지, 사용자가 실제 이체 완료를 확인하는 흐름인지
4. AI 요청 데이터와 로그의 보관·삭제 정책
5. 송금정보 전체 복사의 기본 문자열 형식

## 15. 분석 한계

- 본 문서는 저장소 기준 정적 분석이며 실제 Firebase 콘솔의 배포 규칙, 데이터 건수, Cloud Run 환경변수, 로그와 비용은 조회하지 않았다.
- `firestore.rules`가 실제 운영에 배포되었는지 반드시 콘솔에서 확인해야 한다.
- 의존성이 설치되지 않은 체크아웃 상태여서 TypeScript 검사와 프로덕션 빌드는 실행하지 않았다. `isCustom` 타입 불일치 등은 의존성 설치 후 CI에서 확정해야 한다.
- 운영 데이터 자체는 열람하거나 변경하지 않았다.
