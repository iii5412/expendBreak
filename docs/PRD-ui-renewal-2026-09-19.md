# 진단데이터 기반 UI 전면 개편 제안

작성: 2026-09-19 · 분석 코드: `171df13` · 범위: 분석, 제안, 구현 계획. 앱 및 실제 사용자 데이터 변경 없음.

개정: v1.2 · 주기별 금액 모델 평가 반영. 아래 규칙은 구현할 목표 동작이며 현재 앱에 적용되었다는 뜻이 아니다. 2–4장의 진단 수치는 개편 전 데이터의 분석 결과다.

## 1. 제안의 핵심

**‘이번 주기 돈 상태 → 확인할 항목 → 금액 수정’이 한 흐름으로 이어지는 앱으로 개편한다.**

- 홈은 상황에 따라 ‘쓸 수 있는 돈’, ‘계획상 부족액’, ‘마감 결과’를 대표 숫자로 보여준다.
- 고정지출을 주요 메뉴로 승격하고 월별 금액과 반복 설정을 같은 화면에서 관리한다.
- 고정 항목은 이름·납부일·결제수단 같은 반복 규칙으로만 존재하며, 정확한 금액은 각 급여 주기에 입력한다.
- 새 주기가 시작되면 전 주기의 최종 금액을 입력칸에 제안하고, 사용자는 그대로 확정하거나 바로 수정한다.
- 거래내역, 납부 목록, 홈, 미래 예측이 같은 금액을 읽도록 정합성을 먼저 해결한다.
- 현재 사용 가능액은 최신 주기 금액으로 즉시 재계산한다. 처음 확정한 계획은 비교 기록으로 보존하며 현재 계산을 고정하는 용도로 쓰지 않는다.
- 사용자가 이해해야 할 용어는 `고정 항목`, `이번 주기 금액`, `납부 기록`이다. ‘원본’, ‘발생 일정’, ‘계획 재생성’은 주 흐름에서 숨긴다.

## 3. 8월·9월에서 확인한 사용 패턴

단위: 원. 9월은 진행 중이므로 월 전체 소비를 직접 비교하여 절약률로 해석하지 않는다.

|---|---:|---:|

| 계좌 고정지출, 거래 반영 기준 | 4,321,116 | 4,393,276 |

### 해석

1. **9월 위험의 중심은 생활비 사용률보다 재원 부족이다.** 수입 6,325,830원보다 계좌 고정지출 4,393,276원 + 카드대금 3,037,840원 + 저축 계획 100,000원이 1,205,286원 많다. 생활비 사용 464,275원은 이 부족액과 별도 지표다. 은행 잔액이 확인되지 않았으므로 ‘통장에 실제로 돈이 없다’고 표현하지 않는다.
2. 8월에는 급여 외 수입 3,624,827원이 있었지만 현재 9월 기록에는 없다. 카드대금이 682,160원 줄었어도 9월 재원은 더 부족하다. ‘지난달보다 카드대금 감소’만 강조하면 핵심을 놓친다.
3. 동일한 주기 첫 10일을 비교하면 8/10–8/19 생활비는 1,222,730원, 9/10–9/19는 464,275원이다. 기록 기준 약 62.0% 감소했다. 일회성 지출과 기록 누락 여부를 통제한 결과는 아니므로 습관 개선으로 단정하지 않는다.
4. 8월 생활비 중 ‘기타’는 1,046,500원, 약 38.9%다. 9월도 ‘기타’ 180,500원, 약 38.9%이며 배달음식은 165,700원이다. 작은 도넛 차트보다 ‘기타 7건 분류 확인’ 같은 실행 가능한 분석이 유용하다. 자동 재분류는 하지 않는다.
5. 모든 계좌 잔액은 0으로 저장되어 있고 확인된 계좌는 0/14개다. 합계를 ‘총자산 0원’으로 보여주면 오해를 만든다. `잔액 미입력 · 14개 계좌`라고 표시하고 계획 계산과 분리한다.
6. 9월 정기지출은 계획 포함 기준 33건 중 32건이 완료 상태이고 카드 결제 ‘점심값’ 53,000원 1건만 확인 대기다. 계좌 이체 대상은 모두 완료로 표시되므로 이체 목록 중심 첫 화면은 현재 필요한 작업을 숨긴다.
7. 9/19 현재 미래 날짜 9/21, 9/25, 10/5로 기록된 완료 거래가 8건 있다. 선납 또는 일괄 완료의 결과일 수 있다. 실제 이체 검증 자료가 없으므로 오류로 단정하지 않고, ‘납부 예정일’과 ‘실제 납부일’을 분리하는 설계 근거로 삼는다.

## 4. 금액 변경에서 발견한 구체적인 문제

### P0 — 관리비 금액이 화면에 따라 다름

| 관리비 데이터 | 8월 | 9월 또는 현재 저장값 |
|---|---:|---:|
| 현재 코드의 반복 원본 금액 | 해당 시점의 원본 이력 없음 | 325,280 |
| 월별 일정 예상 금액 | 250,000 | 250,000 |
| 월별 일정의 완료 금액 | 250,000 | 250,000 |
| 연결된 거래 금액 | 250,000 | 325,280 |

9월 일정과 연결 거래의 ID는 정상적으로 연결되어 있지만 금액이 75,280원 다르다. 전체 완료 일정 중 이 유형의 금액 불일치는 1건이다.

코드 재현 결과:

- 홈의 계좌 고정지출 + 카드대금: **7,431,116원**.
- 정기납부 계좌 그룹 합계: **7,355,836원**.
- 차이: **75,280원**.
- 관리비 10월 예정 금액 역시 250,000원이며 현재 이월 함수도 250,000원을 반환한다.

근거: `storage.ts:updateTransaction`은 거래만 갱신하며 연결된 일정을 갱신하지 않는다. `paydayTransfers.ts`와 정기납부 목록은 일정의 `actualAmount ?? expectedAmount`를 읽고, 월 요약은 완료 거래를 반영한다. 기록 시각도 원본 수정 → 일정 생성 → 완료 → 거래 금액 수정 순서에 부합한다. 다만 클릭 이력이 없으므로 정확한 사용자 조작 순서는 추정이다.

**제안:** 완료 항목의 대표 금액은 연결 거래를 기준으로 읽고, 완료 금액 수정 시 거래와 일정을 같은 변경 단위로 저장한다. 기존 불일치는 `납부 목록 250,000원 / 거래 기록 325,280원`의 차이를 보여주고 조정 근거를 남긴다. 실제 납부액이 맞는지 사용자 확인이 필요한 경우에는 조용히 덮어쓰지 않는다.

### P0 — 고정 항목과 주기 금액이 분리되어 있지 않음

`storage.ts:updateOccurrencePlan`은 선택 일정에 `actualAmount`를 저장한 후 같은 원본의 미래 일정 중 개별 수정액이 없는 일정의 `expectedAmount`도 바꾼다. 아직 만들지 않은 달도 `recurringPlans.ts:getCarriedRecurringAmount`에 의해 이전 기록을 물려받을 수 있다.

새 모델에서 고정 항목은 금액을 소유하지 않는다. 이름, 유형, 납부일, 반복 주기, 결제수단, 계좌·카드 연결만 보관한다. 정확한 금액은 `고정 항목 × 급여 주기`에 속하는 값이다. 새 주기의 입력칸에는 전 주기의 최종 금액을 복사해 **제안값**으로 보여주되, 사용자가 확인하기 전까지 정확한 금액으로 간주하지 않는다.

이 구조에서는 ‘이번 달만’ 같은 적용 범위 선택이 필요 없다. 화면에서 바꾼 금액은 항상 현재 보고 있는 주기에만 저장되고, 다음 주기는 그 값을 새 제안값으로 사용할 뿐 자동 확정하지 않는다.

### P0 — 적자인 상태에서 추가 금액 변동이 보이지 않음

9월 확정 계획의 계좌 고정지출은 4,317,996원, 현재 계산은 4,393,276원이다. 그런데 확정 생활비와 재계산 생활비 모두 `max(0, …)` 처리되어 0원이며, `unplannedDelta = 0`이다. 홈의 변경 안내 조건이 이 값만 보므로 75,280원 증가가 표시되지 않는다.

**제안:** 생활비 표시용 0원 제한과 별도로 수입·고정지출·카드대금·저축의 원래 부호 있는 차이를 저장·비교한다. ‘확정 후 고정지출 75,280원 증가’와 ‘계획상 부족액 증가’를 보여준다.

### P1 — 원본 금액과 주기 금액이 서로 경쟁함

| 항목 | 현재 코드의 원본 금액 | 8월 납부 기록 | 9월 연결 거래 |
|---|---:|---:|---:|
| 관리비 | 325,280 | 250,000 | 325,280 |
| 여보_고정지출 | 600,000 | 600,000 | 650,000 |
| 통신비 | 45,000 | 65,000 | 65,000 |
| 가스비 | 10,040 | 12,000 | 12,000 |

원본 금액과 다르다는 사실만으로 오류라고 판단하면 안 된다. 정확한 금액은 그 주기의 값이기 때문이다. 화면은 `전 주기 65,000원에서 가져옴`, `이번 주기 확인 완료`, `납부 기록과 75,280원 차이`처럼 출처와 확인 상태를 알려준다. 반복 항목에 별도의 기준 금액을 유지하지 않는다.

현재 모든 활성 고정지출의 `expenseNature`가 `fixed`다. 새 모델에서는 이 분류와 관계없이 모든 고정 항목이 같은 주기별 금액 확인 흐름을 사용한다. 금액이 일정한 보험료도 전 주기 금액을 한 번에 확정할 수 있고, 관리비·가스비는 같은 화면에서 숫자만 수정한다. 항목별로 별도의 ‘매달 확인’ 모드를 설정할 필요가 없다.

## 5. 새 정보 구조

하단 주요 메뉴: **홈 / 고정지출 / 내역 / 분석**. 거래 추가는 항상 같은 위치의 `+ 기록`, 계좌·카드와 앱 설정은 홈 상단 더보기에서 접근한다. 고정지출 안의 계좌 보기에서도 해당 계좌·카드로 바로 이동한다.

| 화면 | 사용자의 질문 | 기본 구성 |
|---|---|---|
| 홈 | 지금 어느 정도 여유가 있고 무엇을 확인해야 하나? | 주기 표시 → 상황별 대표 금액 → 수입/고정비/카드대금/저축 흐름 → 확인할 일 최대 3개 |
| 고정지출 | 이번 주기 금액이 맞나? 무엇을 바꿔야 하나? | 주기 시작 금액 확인, 상태 필터, 항목별/계좌별 보기, 금액 직접 수정 |
| 내역 | 실제로 무엇을 기록했나? | 생활비/고정지출/카드대금/이체/수입의 역할 구분, 연결된 정기 항목 바로가기 |
| 분석 | 무엇 때문에 달라졌나? | 같은 경과일 비교, 전 주기 대비 변화, 기타 분류 확인, 미래 계획 |
| 계좌·카드 | 어디에 얼마를 준비해야 하나? | 준비 상태와 실제 납부 상태 분리, 미입력 잔액 표시, 카드 사용·청구 금액 구분 |
| 설정 | 반복 규칙을 어떻게 바꾸나? | 고정지출 상세로 연결, 예산과 급여일, 앱 설정. 원본 목록 중복 제거 |

### 홈의 상태별 대표 숫자

- 재원이 충분할 때: `오늘 쓸 수 있는 생활비`와 `이번 주기 남은 생활비`.
- 재원이 부족할 때: `고정지출·카드대금·저축 계획이 수입보다 1,205,286원 많아요`. 보조로 `생활비 사용 464,275원`, `설정 한도 초과 164,275원`을 구분한다. 부족액을 실제 은행 마이너스 잔액이나 앞으로 남은 미납액으로 부르지 않는다.
- 기록 불일치가 있을 때: 대표 숫자 옆 `금액 확인 1건`과 관련 항목으로 가는 동작. 서로 다른 숫자 둘을 설명 없이 노출하지 않는다.
- 마감 주기: `생활비 사용 2,690,140원`, `설정 한도 대비 2,390,140원 초과`, `재원 대비 780,599원 초과`. 오늘 권장액이나 남은 일수 예측은 숨긴다.

대표 영역의 우선순위는 `마감 결과 → 계산 불완전 → 예상 계산 → 확정 입력 기준 계산`이다. 마감 결과에도 미입력·기록 불일치가 있으면 ‘잠정 결과’를 붙인다. 시작 전 주기는 ‘다음 주기 계획’만 표시하고 오늘 사용 권장액은 계산하지 않는다.

| 계산 상태 | 조건 | 홈의 표시와 동작 |
|---|---|---|
| 불완전 | 포함 대상 수입·계좌 고정지출·카드 청구액 중 참고 금액조차 없는 항목이 있거나, 필요한 연결 거래를 확인할 수 없음 | `금액 입력·확인 필요 N건`을 대표 안내로 표시. 오늘 사용 가능액은 `—`이며 계산 가능한 소계와 미포함 항목을 표시 |
| 예상 | 미입력은 없지만 전 주기 제안액·추정 카드대금·미입금 수입 등이 포함됨 | 같은 계산식으로 산출하되 `예상 사용 가능액` 또는 `예상 부족액`이라고 표시하고 추정 근거에 연결 |
| 확인 완료 | 필요한 입력이 모두 확인되고 기록 불일치가 없음 | 최신 금액을 사용한 현재 계산 표시. 실제 계좌 잔액과는 구분 |

금액 불일치가 있지만 연결 거래가 존재하면 대표 금액은 거래 기준으로 통일하고 `기록 차이 확인 중`을 붙여 예상 상태로 낮춘다. 연결 거래를 찾을 수 없는 경우 로컬 캐시 미조회인지 먼저 조회하고, 확인 전에는 해당 금액을 0원으로 대체하지 않는다. 불완전한 소계로 계산한 ‘부족액’ 역시 전체 부족액으로 단정하지 않는다.

### 현재 사용 가능액과 최초 계획의 관계

1. 수입·고정지출·카드대금·저축 확보액은 선택한 주기의 최신 유효값을 사용한다. 완료 항목은 연결 거래, 미완료 항목은 확정 금액 또는 제안 금액을 사용하며 동일 항목을 한 번만 합산한다.
2. 예정 수입은 해당 주기에 명시적으로 확인한 입금 계획만 포함하고 입금 전에는 전체 결과를 예상으로 표시한다. 입금 거래가 연결되면 그 거래가 해당 계획을 대체하며 이중 합산하지 않는다. 정기 수입도 주기별 금액 모델을 사용하되 고정지출 합계와는 분리한다.
3. `생활비 재원 R = 수입 − 계좌 고정지출 − 해당 결제 주기의 카드대금 − 저축 확보액`으로 계산하며 원래 부호를 보존한다.
4. `사용 가능 한도 A = max(0, R)`이다. 사용자가 별도 생활비 한도 L을 설정했다면 `A = min(max(0, R), L)`이다. 기존 설정에서 한도 0은 미설정을 뜻하므로 이관 시 `L = null`로 명시한다. 고정지출의 확정 0원과는 다른 개념이다.
5. `남은 생활비 = A − 이번 주기 생활비 사용액`, `오늘 사용 가능액 = floor(max(0, 남은 생활비) / 남은 날짜 수)`다. 진행 중 주기에서 남은 날짜는 오늘을 포함하고, 마감·시작 전·계산 불완전 상태에서는 오늘 사용 가능액을 표시하지 않는다.
6. `생활비 사용 전 부족액 = max(0, −R)`이다. 생활비 사용액을 이 수치에 섞어 표시하지 않으며 구성항목별 증감을 별도로 설명한다.
7. 최초 확정 계획(`CycleBaseline`)은 비교용 스냅샷이다. 현재 계산의 입력값으로 다시 사용하지 않는다. 금액 수정 시 `처음 계획보다 고정지출 +75,280원`을 표시하며 한도 L, 저축 목표, 최초 스냅샷은 자동 변경하지 않는다. 사용자가 계획을 다시 확정하면 새 비교 스냅샷과 이력을 남기지만 현재 금액 반영에 이 작업을 요구하지 않는다.

따라서 관리비를 250,000원에서 325,280원으로 수정하면 최신 R은 75,280원 감소한다. R이 양수이고 한도 제한에 걸리지 않은 경우 남은 생활비도 같은 금액만큼 감소한다. 이미 R이 음수이면 오늘 사용 가능액은 0원을 유지하되 부족액이 75,280원 증가한다. 한도가 더 낮아 표시 금액이 그대로인 경우에도 고정지출·재원 변화는 표시한다.

9월 추천 확인 항목은 관리비 기록 불일치, 점심값 53,000원 확인 대기다. 카드 이용기간은 3장 모두 미설정이므로 미래 카드대금 예측의 보조 안내로 둔다. ‘우리’ 카드 확정 청구액 1원은 입력 오류일 가능성을 확인할 수 있지만 임의로 0원으로 바꾸지 않는다.

### 고정지출 목록

상단은 `이번 주기 / 고정 항목 설정` 전환이며 첫 화면은 이번 주기다. 주기 생성 직후에는 ‘주기 금액 확인’을 우선 노출하고, 확인 이후에는 `항목별 / 계좌별` 보기를 사용한다. 기본 보기는 항목별이며 사용자가 마지막으로 선택한 보기를 유지한다. 자금 준비가 필요한 항목은 계좌별 보기로 연결하고, 완료가 많은 지금은 확인 필요 항목을 먼저 보여준다.

한 행의 정보는 이름, 이번 주기 금액, 확인 상태, 납부일·결제수단이다. 전 주기와 금액이 달라진 항목에만 차이를 보조 행으로 표시한다. 금액 자체가 44px 이상 터치 영역인 수정 버튼이다. 완료 항목도 금액 수정이 가능하며 완료 취소 후 재등록을 강요하지 않는다.

상태는 목적별로 구분한다:

- 금액: 미입력 / 제안 / 확정. 직접 입력·전 주기 복사는 상태가 아닌 출처다.
- 납부: 미납 / 완료 / 이번 주기 제외. 자금 준비 여부는 별도의 계좌별 정보다.
- 기록 품질: 금액 불일치 / 결제수단 미지정 / 잔액 미입력.

상태를 모두 배지로 쌓지 않고 대표 상태 1개와 필요한 보조 문장만 표시한다.

## 6. 핵심 흐름 — 주기 시작에 확인하고 필요할 때 바로 수정

1. 새 급여 주기의 계획을 생성하면 고정 항목마다 전 주기의 최종 금액을 입력칸에 채운다. 출처를 `8월 주기 납부액에서 가져옴`처럼 표시한다. 계획을 생성하는 조건은 8장의 주기 생명주기 규칙을 따른다.
2. 사용자는 `전 주기 금액 그대로 확정`으로 전체 또는 개별 항목을 확인한다. 달라진 항목은 숫자만 바꾼 뒤 확정한다.
3. 전 주기 금액이 없는 신규 항목은 빈 입력칸과 `금액 입력 필요` 상태로 표시한다. 0원으로 추정하지 않는다.
4. 주기 중 청구서나 납부액이 달라지면 `고정지출 → 항목 금액`을 눌러 같은 입력 화면에서 수정한다.
5. 저장 전에 이번 주기 고정지출 합계와 생활비 재원이 얼마나 바뀌는지 보여준다.
6. `저장`을 누르면 해당 주기의 금액과 요약을 갱신한다. 완료 항목의 정정이면 기존 연결 거래도 함께 갱신하며, 미납 항목의 금액 저장은 거래를 생성하지 않는다. 실행 취소를 제공하고 전 주기 기록은 유지한다.

여기서 ‘주기’는 1일–말일이 아니라 화면에 표시된 급여 주기다. 한 고정 항목이 주기 안에서 여러 번 발생한다면 금액은 각 발생 건에 속하며, 일괄 확인 화면에서도 각각 구분한다.

### 주기 시작 금액 확인 화면 — 1차 핵심 화면

화면의 목표는 사용자가 전 주기와 달라진 항목만 고치고 나머지는 한 번에 확인하는 것이다.

| 영역 | 요구사항 |
|---|---|
| 상단 | `10월 주기 금액 확인 · 10/10–11/9`, 전체 대상 수와 확정·제안·미입력 건수 표시 |
| 항목 행 | 이름, 전 주기 금액과 출처 주기, 이번 주기 입력칸, 금액 상태. 숫자 입력은 행 안에서 가능 |
| 정렬 | 미입력·기록 불일치 우선, 나머지는 납부 예정일순. 입력 중 자동 재정렬하지 않음 |
| 변동 표시 | 입력값이 전 주기와 다를 때만 `+75,280원`처럼 표시 |
| 하단 요약 | 확정 소계, 제안 포함 예상 합계, 미입력 N건, 현재 재원 변화. 카드 구매와 해당 주기의 카드대금 합계를 구분 |
| 주 행동 | `선택한 N건 금액 확정`. ‘제안 금액 전체 선택’으로 같은 금액을 유지할 항목을 한 번에 선택 가능 |
| 보조 행동 | `나중에 확인`으로 나가도 입력 중 초안이 유지되며 홈에 남은 확인 건수가 표시됨 |

360px 모바일에서는 항목명과 상태를 첫 줄에, `전 주기 금액 → 이번 주기 입력`을 둘째 줄에 표시한다. 데스크톱은 같은 정보를 열로 나눈다. 예시 배치는 아래와 같으며 금액은 동작 설명용이다.

```text
10월 주기 금액 확인                 10/10–11/9
확정 0건 · 제안 2건 · 미입력 1건

[선택] 관리비                       제안
전 주기 325,280원     이번 주기 [325,280]
[선택] 통신비                       제안
전 주기 65,000원      이번 주기 [ 65,000]
[    ] 새 보험                      금액 입력 필요
전 주기 기록 없음    이번 주기 [       ]

예상 소계 390,280원 · 미입력 1건 별도
[선택한 2건 금액 확정]     [나중에 확인]
```

입력 초안은 `미저장`으로 표시하며 합계 변경 미리보기에만 반영한다. 저장된 주기 금액과 구분하고 재진입 시 복원한다. 일괄 선택은 유효한 숫자가 있는 미확정·미납 항목만 대상으로 하며 빈칸, 제외, 완료, 충돌 항목은 자동 선택하지 않는다. 미입력이 남아 있어도 선택한 유효 항목만 저장할 수 있다. 저장 실패·충돌 항목은 성공한 항목과 구분해 남기고 재시도로 중복 확정하지 않는다.

**금액 일괄 확정은 납부 완료·계좌 이체·거래 생성을 실행하지 않는다.** 반복 정의의 기존 자동 납부 설정도 제안 금액을 임의로 확정할 수 없다. 1차 개편에서는 신규 자동 납부 실행을 보류하고 명시적 납부 완료 동작으로 처리한다. 기존 완료 거래는 유지한다.

### 금액 상태와 납부 상태

| 구분 | 상태 | 의미와 합계 처리 |
|---|---|---|
| 금액 | `missing` · 미입력 | 금액이 null. 0원 대체 금지. 포함 대상이면 계산 불완전 |
| 금액 | `suggested` · 제안 | 전 주기 또는 이관 자료에서 가져온 미확인 금액. 예상 합계에 포함 |
| 금액 | `confirmed` · 확정 | 사용자가 확인한 해당 주기의 금액. 확정 0원도 유효 |
| 납부 | `unpaid` · 미납 | 금액 상태와 독립. 확정했다고 완료로 바뀌지 않음 |
| 납부 | `paid` · 완료 | 확인된 양수 거래와 연결됨. 완료 금액은 연결 거래가 기준 |
| 납부 | `skipped` · 이번 주기 제외 | 금액과 이전 상태를 보관하되 합계에서 제외. 항목 정의 유지 |

자금 준비는 납부 상태를 바꾸지 않는다. 확정 0원·미납은 UI에서 `납부 없음`으로 표시하며 거래를 만들거나 미납 알림을 발생시키지 않는다. 제외 복원은 저장된 금액 상태로 돌아가며 다시 0원으로 초기화하지 않는다. 완료 항목을 제외하려면 완료 취소로 거래를 해제한 뒤 제외한다.

상태 전이는 `미입력/제안 → 금액 확인 → 확정·미납 → 납부 완료 → 확정·완료`다. 납부 완료 시 미확정 금액이 남아 있으면 같은 화면에서 금액을 명시적으로 확인받아 확정과 완료를 함께 저장할 수 있다. 완료 취소 시 거래 연결을 해제하되 최종 확정 금액은 유지한다. 납부일이 미래라는 이유만으로 자동 완료하지 않는다.

### 완료 기록의 금액을 수정할 때

- `납부 완료 기록을 함께 수정합니다`를 명시한다.
- 납부 상태와 거래 ID는 유지하고 금액·연결 일정·변경 이력을 함께 저장한다.
- 실제 납부일은 명시적으로 바꾸지 않는 한 유지한다.
- 현재 계산은 수정된 금액을 즉시 반영한다. 최초 확정 계획은 비교 기록으로 유지하고 `최초 계획 대비 변화`를 보여준다. 금액 반영을 위해 ‘확정 계획에도 반영’을 다시 누르게 하지 않는다. 사용자 생활비 한도와 저축 목표 자체는 별도 설정이다.

### 다음 주기의 제안값

- 다음 주기는 직전 주기의 연결 거래 금액을 우선 제안한다. 거래가 없으면 그 주기에 사용자가 마지막으로 확정한 금액을 사용한다.
- 직전 주기가 `이번 주기 제외`였거나 금액 미입력 상태라면, 그보다 앞선 가장 최근의 최종 금액과 주기를 명시해 제안할 수 있다.
- 제안값은 자동 확정하지 않는다. 사용자가 `그대로 확정`하거나 수정해야 이번 주기의 정확한 계획 금액이 된다.
- 전 주기 금액을 새 주기에 복사한 뒤 전 주기 기록을 수정해도 이미 열린 새 주기의 값은 조용히 바뀌지 않는다. 변경 사실과 다시 가져오기 동작을 제공한다.
- 금액 미확인, 확정 0원, 이번 주기 제외를 서로 다른 상태로 다룬다.
- 제안값만 있는 주기는 다음 주기의 확정 근거로 쓰지 않는다. 가장 최근의 완료 거래 또는 확정 주기까지 거슬러 올라가 출처 주기를 표시하고, 아무 근거도 없으면 빈칸이다. 불일치·미조회 거래는 확인되기 전 제안 근거로 사용하지 않는다.
- 주간 반복의 전 주기 제안은 같은 항목의 발생 순번끼리 대응한다. 이전 주기보다 발생 건수가 많으면 추가 건은 최근 확정 1회 금액을 출처와 함께 제안하며 합계를 각 건에 복사하지 않는다. 제안값의 30% 차이 등을 이유로 사라진 원본 금액으로 되돌리는 기존 규칙은 폐기한다.

## 7. 시각 디자인 방향

컨셉은 **큰 핵심 숫자 하나와 읽기 쉬운 지출 명세**다. 한국어 중심으로 정리하고, 작은 영문 장식 제목·그라데이션·색상 배지를 줄인다.

- 홈은 대표 수치 1개, 재원 흐름 4행, 다음 행동 최대 3개로 첫 화면을 구성한다.
- 본문 14–16px, 대표 금액 32–40px, 숫자 우측 정렬 및 고정폭 숫자를 사용한다. 필수 정보에 10px 글자를 쓰지 않는다.
- 일반 상태는 중립색, 주 행동은 한 가지 강조색, 확인 필요는 황색, 부족·오류만 적색으로 표현한다.
- 카드 안에 카드를 겹치기보다 구분선이 있는 목록을 사용한다.
- 금액 변경은 전체 입력 폼 대신 짧은 하단 시트로 처리하고, 계좌·주기·이름 등의 고급 설정은 상세에서 연다.
- 360px와 412px Android 화면을 우선 설계하고 태블릿/데스크톱은 목록과 상세를 두 열로 배치한다.
- 다크·라이트, TalkBack, 글자 확대, 키보드와 하단 버튼의 겹침, Android 뒤로가기를 검증한다.

## 8. 구현 설계

### 공통 금액 판정

화면마다 금액 우선순위를 직접 구현하지 않고 공통 판정 함수를 둔다. 반환값은 금액, 출처, 확정 여부, 불일치 여부, 연결 거래, 적용 주기다.

우선순위는 완료 연결 거래 → 해당 주기의 확정 금액 → 전 주기에서 가져온 제안 금액이다. 고정 항목 자체의 금액은 우선순위에 존재하지 않는다. 예상액은 어느 주기의 어떤 값에서 가져왔는지 별도 저장한다. 카드 청구액과 카드 구매액은 다른 항목이며 합산 시 중복하지 않는다.

### 데이터 모델

다음 정보와 제약을 저장 모델에 포함한다. 필드명은 조정할 수 있지만 금액 상태·납부 상태·금액 출처를 합치지 않는다.

- 고정 항목 정의: 이름, 유형, 반복 일정, 납부일, 결제수단, 계좌·카드 연결. 금액 필드 없음.
- 주기 정의: 변경되지 않는 `cycleId`, 표시 월 `cycleYearMonth`, 시작일·종료일 스냅샷, 생성 여부, revision.
- 주기별 발생 건: `itemId`, `cycleId`, `slotId`, `plannedAmount: number | null`, `amountStatus`, `amountSource`, `sourceCycle`, `sourceRevision`, `confirmedAt`, revision. 누락 거래·금액 불일치는 금액/납부 상태와 별도의 `integrityIssue`로 보관한다.
- 납부: 예정일과 실제 납부일, 연결 거래 ID, `paymentStatus`. 실제 납부 금액은 연결 거래가 정본이며 화면마다 별도로 저장한 복제 금액을 우선하지 않는다.
- 변경 이력: 전/후 금액, 대상 주기, 시각, 변경 operation ID, 실행 취소용 전 상태.

`(계정, itemId, cycleId, slotId)`는 유일하다. 월간 항목은 주기당 1개 slot, 주간 항목은 예정 발생 건마다 고정 slot을 부여한다. 예정일을 바꿔도 slot과 거래 ID를 다시 만들지 않는다. 주기 중 수동 추가 건에는 별도 고정 slot을 부여한다. 제외 여부와 관계없이 유일성 제약은 유지한다.

### 주기 생성과 항목 변경 규칙

| 사건 | 처리 |
|---|---|
| 현재 급여 주기 시작 후 첫 접속 | 현재 주기 계획이 없으면 한 번 생성하고 금액 확인 화면으로 연결. 재접속·재시도·다른 기기 접속으로 중복 생성하지 않음 |
| 미래 주기 또는 예측 조회 | 읽기 전용 투영. 조회만으로 일정·금액·확정 계획을 저장하지 않음 |
| 미래 주기의 `미리 준비하기` | 사용자의 명시적 동작으로 해당 주기 계획을 한 번 생성. 나중에 그 주기가 시작되어도 입력한 값을 재생성하지 않음 |
| 접속하지 않은 과거 주기 | 새 완료 기록을 자동 생성하지 않음. 과거 계획이 필요하면 사용자가 해당 주기에서 명시적으로 생성 |
| 항목 추가 | 현재 진행 주기의 `이번 주기에도 추가`를 기본 선택하고 결과를 저장 전에 표시. 선택 시 이번 주기에 미입력 건 추가. 해제 시 다음 주기부터 참여 |
| 항목 종료·삭제 | 정의는 보관하고 다음 미생성 주기부터 제외. 현재와 미리 준비한 미래 계획은 유지하고 대상 목록을 안내. 해당 계획에서 제외하는 동작은 별도로 제공 |
| 이름·계좌·납부일 변경 | 이후 생성분에 적용. 기존 미완료 건에도 반영하려면 대상 주기를 선택해 미리보기 후 적용하며 금액·확인 상태는 유지. 완료 건의 정보는 기록 정정으로만 변경 |
| 납부일의 주기 경계 이동 | 현재 건의 소속 주기를 자동 변경하지 않음. 다른 주기로 옮기려면 충돌을 검사하는 명시적 이동 필요. 변경 전후 동일 건을 중복 생성하지 않음 |
| 급여일 변경 | 1차에서는 현재 및 저장된 미래 주기가 모두 끝난 뒤의 첫 미생성 주기부터 적용. 첫 전환 주기는 마지막 저장 종료일 다음 날부터 새 급여일 기준 다음 경계 전날까지로 구성해 날짜 공백·중복을 만들지 않음. 미리보기에서 시작·종료일 표시 |

과거 주기의 날짜 범위와 기록 소속은 현재 사용자 설정을 읽어 다시 계산하지 않는다. 예정된 의무는 계획 소속 주기를 유지하고, 실제 출금은 실제 납부일의 현금 흐름에 나타난다. 조기 납부·늦은 납부가 있으면 내역에 계획 주기를 함께 표시하며 두 보고서의 차이를 설명한다. 같은 범위의 집계끼리 일치시키되 서로 다른 의미의 합계를 무조건 같게 만들지 않는다. 급여일 변경으로 한 달에 두 주기가 시작되면 `전환 주기`와 실제 날짜를 표시하며 표시 월을 유일 키로 사용하지 않는다.

### 미래 예측의 금액 기준

- 저장된 미래 주기는 그 주기의 완료·확정·제안·제외 상태를 그대로 사용한다. 현재 주기 수정이 이 값을 자동 변경하지 않는다.
- 미생성 주기는 최신 유효 항목 정의와 최근 최종 금액으로 읽기 전용 예상치를 만든다. 출처 주기와 `미확정 예상`을 표시하며 자동으로 정확한 금액이 되지 않는다.
- 근거 금액이 없으면 `미포함 N건`을 표시하고 ‘전체 예상 합계’ 대신 ‘계산 가능한 예상 소계’라고 부른다.
- 카드 고정 구매는 카드 이용 기록·예정 사용액 쪽에 반영하고 청구 이용기간에 따라 결제 주기로 이동한다. 계좌 고정지출에 다시 더하지 않는다. 카드 이용기간이 미설정이면 추정 기준을 표시하며 정확한 결제월로 단정하지 않는다.
- 월 선택을 바꾸더라도 동일한 입력 revision에 대한 동일 대상 주기의 예측 결과는 같아야 한다. 예측 조회는 저장·이월·납부 동작을 실행하지 않는다.

### 기존 데이터 전환과 구버전 호환

`RecurringTemplate.defaultAmount`는 v2 계산에서 폐기한다. 기존 `actualAmount`의 계획 수정과 납부 의미를 아래 표로 분리한다. 원본은 백업과 복구 검증을 위해 보존하며 새 모델의 계산 근거로 계속 사용하지 않는다.

| 기존 데이터 | v2 전환 |
|---|---|
| 완료 일정 + 정상 연결 거래 | 금액 확정·납부 완료. 거래 ID와 실제 거래 날짜·금액 보존 |
| 완료 일정과 거래 금액 불일치 | 연결 거래로 대표 금액 통일, 불일치 표시와 두 원본값 보존. 다른 값을 선택하면 명시적 정정 operation으로 저장 |
| 완료 일정의 연결 거래가 없음 | 누락 이력 조회 후에도 없으면 ‘기록 확인 필요’. 거래를 임의 생성하거나 미납으로 조용히 변경하지 않음 |
| 미완료 일정에 명시적 수정액이 있음 | 해당 주기 확정 금액·미납으로 이관. 다른 미래 주기로 재전파하지 않음 |
| 미완료 일정에 예상액만 있음 | 해당 주기 제안 금액·미납으로 이관. 정확한 금액으로 자동 확정하지 않음 |
| 건너뜀 일정 | 이번 주기 제외, 기존 금액과 출처 보존 |
| 일정 없이 항목 원본 금액만 있음 | 처음 생성하는 주기에 한해 `legacy_template` 제안값으로 사용할 수 있음. 이후 전 주기 최종값 규칙을 따름 |
| 기존 예산·확정 계획 | 한도 및 저축 설정 보존, 확정 계획은 비교 스냅샷으로 이관. 현재 사용 가능액의 고정값으로 사용하지 않음 |

과거 확정 시각의 근거가 없으면 `confirmedAt`을 만들어내지 않고 이관 시각과 `legacy` 출처를 구분한다. 기존 자동 납부 설정은 보관하되 제안액의 자동 거래 생성은 중지하며 업데이트 후 금액 확인 화면에 변경 안내를 제공한다.

전환 절차는 다음을 따른다.

1. 이 기기의 미전송 작업을 동기화하고 계정의 전환 잠금을 획득한다. 전환 중 기존 저장소의 쓰기를 서버에서 차단하고 클라우드 기준 스냅샷과 revision을 기록한다. 오프라인에서는 전환을 시작하지 않는다.
2. 기존 자료를 보존한 채 v2 전용 저장 영역에 결정적 ID로 복사한다. 변경되는 주기·항목뿐 아니라 연결 거래와 관련 설정의 쓰기 경계도 포함하여 구버전과 v2가 같은 기록을 각기 수정하지 못하게 한다.
3. 거래 수·ID·금액, 주기별 합계, 제외 상태, 연결 관계를 전환 전후 검증한다. 기존 화면 간 불일치와 최신 계산 정책 전환으로 인한 차이는 허용 목록에 근거를 남기고 그 밖의 차이는 활성화를 막는다.
4. 검증 통과 후 계정의 활성 schema를 v2로 한 번 전환한다. 같은 migration ID로 재실행해도 중복 문서·거래가 생기지 않는다. 클라이언트별 메모리 플래그만으로 완료를 판단하지 않는다.
5. v2 활성 후에는 구버전 저장 경로의 쓰기를 서버에서 거부한다. 구버전은 업데이트가 필요함을 안내하며, 접속하지 않았던 기기의 미전송 작업은 자동 재적용하지 않고 원본을 보존해 업데이트 후 충돌 검토 대상으로 제시한다.

복구는 활성화 전 실패라면 staging 작업을 재개하거나 기존 schema로 돌아갈 수 있어야 한다. 활성화 후 v2 변경이 있으면 과거 백업으로 덮어쓰지 않고 변경 이력을 보존한 복구 또는 수정 버전 배포를 사용한다. 구버전 쓰기 차단·백업 검증·재실행 검증이 마련되기 전에는 운영 데이터 전환을 릴리스하지 않는다.

정기납부 수정, 내역 수정, 카드대금 수정, 동기화 복원 모두 같은 도메인 동작을 거치게 한다. 완료 정정은 거래·주기 건·이력을 한 operation으로 저장하고 expected revision이 다르면 충돌로 돌린다. 동일 operation의 재시도는 중복 적용하지 않는다. 오프라인에서는 operation 전체를 대기열에 넣어 로컬 계산에 반영하고 `동기화 대기`를 표시한다. 서버가 충돌을 반환하면 상대 값을 조용히 덮어쓰지 않고 비교 후 적용하며, 실행 취소도 현재 revision을 확인하는 역변경으로 수행한다.

## 9. 실행 순서와 완료 조건

아래 일정은 1인 개발 기준의 재산정용 가정이다. 데이터 전환·구버전 차단·주기 시작 화면을 포함해 약 15–22 작업일의 범위로 잡되, 1단계의 전환 실험과 동기화 검증 후 다시 산정한다. 기존 10–15일 추정은 확정 일정으로 사용하지 않는다.

| 순서 | 범위 | 예상 | 완료 기준 |
|---|---|---:|---|
| 1 · P0 | 공통 금액 판정, 최신 계산 규칙, 전환·구버전 차단 실험 | 2–3일 | 75,280원 차이 재현·검출, 이관 상태표와 복구 방법 검증 |
| 2 · P0 | 주기 생명주기·금액/납부 상태·원자적 수정·오프라인·실제 전환 구현 | 4–6일 | 금액 중복·소실 없는 전환, 충돌·재시도·구버전 쓰기 차단 통과 |
| 3 · P0 | 주기 시작 일괄 확인, 금액 수정 시트, 홈 계산 상태의 최소 반영 | 3–4일 | 금액 확인이 거래를 만들지 않음, 미입력 때 사용 가능액을 확정적으로 표시하지 않음 |
| 4 · P1 | 홈과 전체 내비게이션, 공통 디자인 적용 | 3–4일 | 첫 화면에서 주기·돈 상태·다음 행동을 설명 가능 |
| 5 · P1 | 내역·분석·계좌·설정 정리, Android 실기기·전환 리허설 | 3–5일 | 예측 일관성, 접근성·키보드와 데이터 전환 수용 기준 통과 |

1차 제공 범위는 1–3단계다. 금액 수정과 데이터 신뢰성을 먼저 완성한 뒤 같은 디자인 언어로 전체 화면을 전환한다. 새로운 AI 기능, 은행 연동, 영수증 처리 개편, 외부 소개 페이지는 이번 개편의 필수 범위가 아니다.

### 필수 수용 시나리오

1. 관리비의 기존 250,000원/325,280원 불일치를 감지한다. 사용자가 선택한 값으로 정리하면 목록·거래·홈·예측이 일치하고 8월 기록은 유지된다.
2. 통신비의 9월 금액을 바꿔도 8월 기록과 이미 열린 다른 주기의 금액을 덮어쓰지 않는다.
3. 10월 주기(10/10 시작)의 계획을 생성하면 9월의 최종 통신비가 제안값으로 보이지만 `미확인` 상태다. 미래 월을 단순 조회할 때는 아무 기록도 생성하지 않는다.
4. 신규 고정 항목은 금액 없이 저장할 수 있으며, 해당 주기 계획에 포함되면 `금액 입력 필요`로 표시된다. 미입력 금액과 확정 0원을 구분한다.
5. 완료 금액 수정은 새 거래를 만들지 않는다. 거래·일정 한쪽만 성공하거나 재시도로 두 번 적용되지 않는다.
6. 금액 변경 전후 모두 생활비 재원이 0원이어도 증가한 부족액과 고정비 차이를 표시한다.
7. 재원 부족 1,205,286원, 생활비 사용 464,275원, 설정 한도 초과 164,275원을 서로 다른 뜻으로 표시한다. 실제 통장 잔액이라고 부르지 않는다.
8. 카드 청구액 수정과 카드 고정 구매액 수정의 영향 주기를 구분하고 카드대금을 생활비에 다시 더하지 않는다.
9. ‘금액 모름’, ‘확정 0원’, ‘이번 주기 제외’가 구분된다. 미래 납부 예정 건을 완료 처리할 때 실제 납부일을 확인하며 미래 날짜를 실제 납부일로 자동 복사하지 않는다.
10. 8월 마감에는 오늘 사용 권장액이 없고, 9월 비교는 같은 경과일 기준을 기본으로 한다.
11. 360px 화면, 200% 글자 확대, TalkBack, 키보드, Android 뒤로가기, 다크/라이트에서 핵심 작업이 가능하다.
12. 실행 취소·새로고침·앱 재실행·오프라인 재접속 후에도 주기별 금액과 확인 상태가 유지된다.
13. 제안 금액 30건을 한 번에 확정해도 거래 수와 납부 상태는 변하지 않는다. 이미 확정·완료·제외된 항목과 빈칸은 덮어쓰지 않는다.
14. 신규 보험 금액이 비어 있으면 홈의 오늘 사용 가능액은 `—`이고 미입력 건수를 표시한다. 전 주기 금액 제안만 남아 있으면 예상 금액으로 표시한다. 금액 입력 후 상태와 합계가 함께 바뀐다.
15. 관리비 75,280원 증가가 양수 재원에서는 최신 재원을 감소시키고 음수 재원에서는 부족액을 증가시킨다. 최초 계획 스냅샷과 사용자 한도는 유지되며 별도 반영 버튼 없이 계산에 적용된다.
16. 두 기기가 동시에 주기를 생성하거나 동일 작업을 재시도해도 `(itemId, cycleId, slotId)`가 중복되지 않는다. 주간 4회→5회 주기의 추가 건도 금액 합계를 잘못 복사하지 않는다.
17. 항목 납부일을 수정해도 동일 건의 금액·확인 상태·연결 거래가 유지된다. 급여일 변경 전환 주기에 날짜 공백·중복이 없고 과거 거래가 재분류되지 않는다.
18. 동일 입력 revision으로 8월과 9월 화면에서 조회한 같은 미래 주기의 예측은 같다. 예측 조회 전후 저장된 문서 수와 revision은 변하지 않는다.
19. 전환 상태표의 각 유형을 포함한 복사 데이터로 migration을 두 번 실행해도 거래 ID·건수·금액이 보존된다. 75,280원 불일치는 숨기지 않고 확인 대상으로 남는다.
20. v2 전환 뒤 구버전이 원본 금액·거래를 쓰려 하면 서버에서 거절된다. 구버전 기기의 미전송 자료는 삭제하지 않고 업데이트 후 검토 가능해야 한다.
21. 완료 금액 수정 중 네트워크 단절·중복 재시도·다른 기기 수정이 발생해도 거래와 주기 건이 서로 다른 값으로 확정되지 않는다. 실패·충돌·대기 상태와 복구 결과를 사용자에게 표시한다.

### 성공 지표

- 고정지출 금액 변경: 앱의 고정지출 목록에서 3개 주요 동작 이내, 입력 포함 목표 10초 이내.
- 주기 시작 확인: 30개 중 금액이 다른 항목 3개를 수정하고 나머지를 일괄 확정하는 과업을 목표 60초 이내 완료. 사전 사용성 측정으로 검증하며 보장된 성능으로 주장하지 않는다.
- 대표 금액 이해: 사용자가 5초 안에 ‘설정 한도 초과’와 ‘계획상 재원 부족’을 구분한다.
- 동일 항목의 화면별 금액 불일치: 0건.
- 현재 주기의 수정액이 미래 주기에 자동 확정되는 사례: 0건.
- 정상 변경 시 전체 월 계획을 재생성해야 하는 사례: 0건.

## 10. 이번 작업의 산출물과 한계

이 문서는 구현 목표와 수용 조건이며 앱 코드를 바꾸지 않았다. 진단파일은 로컬에서만 분석했다. 실제 금융기관 데이터, 사용자의 클릭 이력, 사용성 테스트는 없으므로 납부 사실·입력 의도·사용성 향상 수치를 검증 완료로 주장하지 않는다. 기존 대화형 시안은 개별 완료 금액 수정만 보여주는 부분 시안이다. 이번 개정에서 추가한 주기 시작 화면의 표·배치와 계산 상태 규칙을 구현 기준으로 삼으며, 기존 시안이 전환·일괄 확인·동기화 요구사항까지 구현한 것으로 간주하지 않는다.
